# zord-multi-agent-review — Defaults (full text)

> Reference file for [`../SKILL.md`](../SKILL.md) (zord-multi-agent-review). SKILL.md's `-h` table carries each flag default and its §4 the roster and output rules; this file is §4 in full — edge cases, rationale, and the measurements behind each value. Load it before starting a loop (its "Loop defaults" define what carries between rounds), before changing any default, and when a caller asks why a default is what it is.
> The `-h` table in SKILL.md is canonical for flag values and defaults. If this file disagrees, the `-h` table wins; fix this file.

## 4. Defaults

- **Default mode on a `pr` target = loop** (one review→fix round at the default `--max-iterations 1`; re-review rounds only above it; mutating, confirmation-gated). All other targets, and any `--no-loop` run, are one-shot read-only.
- **Reviewer roster.** When `--reviewers` is supplied, use it verbatim. When it is
  omitted, resolve the roster with **context-aware selection** — see
  `refs/multi-agent/context-aware-selection.md` (lanes/caps) and
  `refs/multi-agent/lane-agent-table.md` (lane→agent). Review uses the soft cap of
  6 per slice. If selection cannot run (no resolvable signals), fall back to the
  static safety-net roster: `architect-reviewer`, `critical-thinking`,
  `silent-failure-hunter`, `security-reviewer`, `penetration-tester`.
  `penetration-tester` fills the `L-REDTEAM` lane and is the one safety-net name
  allowed to be absent from the pool without hard-failing — drop it, note the gap,
  run the other four. Absent means the lookup (`refs/multi-agent/agent-catalog-lookup.md`)
  ran and did not find it. A listing that failed is not a pool — it makes every
  agent look absent at once — so a lookup error is a hard-fail to fix before
  dispatch, never grounds to drop a lane.
  (The `L-REDTEAM` lane is forced whenever any `risk_flag`
  fires; it is **not** the same as the `L-ADVERSARIAL` floor lane, which is
  `critical-thinking` and produces assumptions rather than severity-tagged
  findings. See `refs/multi-agent/lane-agent-table.md`.)
- **Synthesizer**: `knowledge-synthesizer`
- **Directory file-count cap**: 50 (override with `--max-files <n>`)
- **Slice fan-out cap**: 6 slices per invocation (override with `--max-slices <n>`); each slice spawns the full roster in parallel.
- **PR diff size warning threshold**: 100 KB (warn on stderr, do not auto-truncate)
- **Report file**: written by default to `<git-root>/.claude/reviews/<YYYY-MM-DD>-<slug>.md` — `<git-root>` the primary checkout, the directory kept git-ignored — slug derived from the target (§5A.1 step 10). A review nobody can find once the transcript scrolls is a review that did not happen, and the asymmetry is decisive — an unwanted file costs one `rm`, a lost review costs the whole run. `--no-write` opts out; `--write-to <path>` overrides the path. **Committing a report is rare and never the default** (decision #86): `--write-to` a tracked path such as `docs/reviews/` is the explicit opt-in, and the commit is yours to make.
- **PR comment**: a `pr` target posts exactly one comment carrying the report — one-shot via §5A.7, loop via §10.7. It is the primary destination; the file is a local copy. Both are produced, and `--no-write` does not suppress the comment. `--no-comment` opts out.
- **Default-path collision**: same target reviewed twice on the same day → append `-2`, `-3`, … to the slug rather than refusing. The caller did not choose this path, so a refusal would be a failure they cannot act on.
- **Security findings in a file git does not ignore.** `security-reviewer` is in the default roster, so a report can name a live unremediated vulnerability with file and line — and committing it writes an exploit map into history that a later `rm` cannot reach. The default path is ignored, so this arises only when the written path is not: a `--write-to` tracked path, or §5A.1 step 10's ignore step failing. Still write the file; losing the findings is worse. But say so in the closing output (§5A.7) and hold the file out of a commit until the findings are fixed.
- **`--write-to` overwrite policy**: refuse if destination exists, unless `--force` is also set
- **Mode preset**: when `--mode <name>` is supplied without `--reviewers`, the mode's `reviewers` list replaces the default roster above; when supplied without `--synthesizer`, the mode's `synthesizer` (if any) replaces the default synthesizer. Explicit flags always override the preset.
- **Prompt prelude**: when `--prompt-prelude <path>` is supplied, the file's contents are prepended verbatim to every reviewer brief AND the synthesizer brief under a `## PROJECT PRELUDE` section (see §5A.3 and §5A.6). Max prelude size 16 KB; absent flag = no prelude (briefs render as today).
- **Reasoning lenses**: absent `--lenses` = no lens slots and no `## REASONING STANCE` block (briefs render as today). When supplied, each slug adds one `general-purpose` reviewer to the roster resolved above — lenses never replace `--reviewers`, a `--mode` preset, or the default roster. The steel-man stance is not separately configurable: it is on whenever lenses are.
- **Diff target**: `diff` resolves to `git diff` against the working tree; with `--staged`, to `git diff --staged`. Both run from `git rev-parse --show-toplevel`. Empty diff = hard-fail (nothing to review).

**Execution-locus defaults (one-shot runs):**

- **A one-shot review runs in a dispatched orchestrator subagent by default**, on **every** target — `file` and `spec` included. `--inline` opts out. The caller's context receives the synthesized report and nothing else; reviewer, refuter, and synthesizer transcripts stay in the orchestrator's window where they belong.
- **The loop coordinator is never dispatched.** It mutates — edits, commits, pushes — and its confirmation gate needs a human to prompt. Loop *rounds* already run in their own subagent (§10.2); that is layer 1 of the same two-layer contract, which is why `--in-loop` forces `inline`.
- **The subagent returns a summary and the report's path.** The file holds the complete synthesized document, every section, every finding, every refuter rationale; with no file, the return is that document, verbatim. §7c's brief states the contract and §5A.0 defines the caller-side integrity check that catches a report that isn't complete.
- **A depth failure degrades loudly.** If the orchestrator cannot spawn workers, it returns `DISPATCH-FAILED: Agent tool unavailable in subagent context` and the caller re-runs inline with a one-line note — it never accepts a single-agent report dressed as a multi-lens review. If it can spawn them but cannot finish, it returns `INCOMPLETE: <reason>`, handled the same way.
- **EVERY `Agent` dispatch in this skill sets `run_in_background: false`. Every one, at every layer, with no exceptions.** That means the orchestrator subagent (§5A.0), every reviewer and lens slot and their re-dispatches (§5A.4), every refuter (§5A.5a), the synthesizer (§5A.6), the report adversary (§5A.6a), the per-round loop subagent (§10.2), every coverage re-dispatch (§10.3), every fix applier serial and parallel (§10.4, §10.4a), and every fix verifier and its retry (§10.4b). This rule applies to every `Agent` call issued anywhere in this skill.

  A background child's completion notification goes to the **top-level session**, not to the agent that spawned it. So a backgrounded dispatch ends the spawning agent's turn immediately: it is never re-invoked, everything downstream of the dispatch never runs, and the caller gets either nothing or a "waiting on the reviewers" note that is not a progress report and has nothing to wait for.

  **This rule is stated as a universal because it was previously stated as a list of four roles, and that is exactly how it failed.** PR #67 fixed the four worker roles it enumerated — reviewers, refuters, synthesizer, report adversary — while the orchestrator dispatch and the per-round loop subagent, the two calls that each carry an *entire review*, were never covered and kept losing runs. A reader checking membership in a list will conclude the call in front of them is not on it. There is no list to check: if it is an `Agent` call, it blocks.

**Adversarial refutation defaults (all targets, both modes):**

- **Off by default; `--adversarial` enables it.** The stage is the most expensive thing this skill does (~4.3× median session cost — "Why it is opt-in" in `references/adversarial-rationale.md`), and its guarantee is only load-bearing where a false finding drives an irreversible action with no human in between. When it is off, findings go straight from reviewers to the synthesizer and the report carries no refutation tags, no `## Refuted Findings` section, and no refutation arithmetic in the Executive Summary.
- **Recommend it, don't force it.** When a caller starts a **looping `pr` run with `--yes`** (unattended auto-fix — the §10.3 path where a false HIGH becomes a real commit) **without** `--adversarial`, emit one stderr line: `note: refutation is off; unattended auto-fix will act on unchallenged findings — pass --adversarial to verify them first`. State it once at loop start, never per round, and never block on it.
- **When on, every severity is refuted.** A MEDIUM that survives attack is worth more than one that was never challenged, and MEDIUMs are exactly what the loop's coordinator-judgment branch (§10.3) acts on.
- **Refuter count is severity-scaled**, not uniform: **3 per CRITICAL/HIGH** (override with `--refuters`, range 1–5), **2 per MEDIUM/LOW** (fixed). Both tiers use the same arithmetic — a strict majority with a floor of two (§5A.5a step 4): at 3 refuters, two refutations drop a finding; at 2, both must refute. **No tier, and no `--refuters` value, lets a single refuter kill a finding.** Scaling the count rather than skipping low severities is what makes "refute everything" affordable; a flat 3-per-finding on a 30-finding review is 90 agents for no added discrimination on nits.
- **Refuter diversity is by lens, not by agent.** All refuters use the same `subagent_type` (`critical-thinking` by default) and are differentiated by the attack lens assigned in their brief — evidence / scope / reachability (§5A.5a step 3). Three lenses catch three distinct failure modes; three copies of the same prompt mostly agree with each other, and requiring three *distinct* skeptic agents would make the stage depend on pool composition.
- **The MEDIUM/LOW lens pair is signal-dependent.** CRITICAL/HIGH always get all three lenses. At MEDIUM/LOW the two slots are **evidence + reachability** when any `risk_flag` fired for the target, and **evidence + scope** otherwise — because the dominant false positive differs by context: on a money/keys/irreversible path it is the unreachable claim, off it the out-of-scope one. Same agent count either way; only which lens fills slot two changes. Unknown signals default to the reachability pair.
- **Total fanout budget**: `--max-refuters`, default **20**, **per review pass**. Refuter dispatch batches at the 16-per-turn ceiling from `refs/multi-agent/fanout-consolidation.md`, so 20 is ≤2 dispatch turns. On overflow, degrade lowest-severity-first and report every skipped finding as `UNVERIFIED` (§5A.5a step 2). **The budget does not aggregate across loop rounds** — it is forwarded verbatim to each inner pass, so a 3-round loop at the default can dispatch up to 60 refuters overall. That is the intended reading (each round is an independent review and must be independently verified), but it is the single easiest way to be surprised by cost: budget a loop as `--max-iterations × --max-refuters`.
- **Expect an `UNVERIFIED` tail on finding-rich reviews, and read it as such.** At 2 refuters per MEDIUM/LOW, a budget of 20 covers roughly 8–10 findings; beyond that, degradation starts skipping MEDIUM and LOW groups. An `UNVERIFIED` tag means *nobody challenged this*, **not** *this survived challenge* — the Executive Summary must state the arithmetic (§8) so a reader never mistakes an unverified count for a validated one. Raise `--max-refuters` when a run needs full coverage.
- **UNCERTAIN upholds.** A refuter that cannot decide does **not** count as a refutation. The asymmetry is deliberate: dropping a real CRITICAL is terminal and silent, while carrying a false one costs a human one paragraph of reading. Ambiguity must therefore fail *toward* keeping the finding. (This is the opposite of the default-to-refuted convention used in generic verifier fan-outs, which optimize for precision over recall; a merge gate needs the reverse.)
- **Refutation runs before the severity budget.** Order is dedupe-for-assignment → refute → synthesize (which applies `--high-cap`). Capping HIGHs before refuting would spend the budget on findings that are about to be dropped.

**Report adversary defaults (all targets, both modes):**

- **On by default; `--no-report-audit` opts out.** One agent, once per review pass, auditing the finished report against the reviewer outputs and refutation verdicts (§5A.6a). The asymmetry with refutation is deliberate and is about scaling, not principle: refutation spawns work proportional to finding count (28 refuters on a 13-finding file), while this is exactly one agent whatever the report contains — a few percent of a run, not 4×.
- **It attacks the document, not the code.** Its whole subject is synthesis fidelity: unapplied refutation outcomes, dedupe damage, budget-distorted severities, an Executive Summary that contradicts its own body. Nothing else in the pipeline looks at these, because every one of them is created by §5A.6 after the last reviewer has finished.
- **Advisory, appended, never blocking.** It emits a `## Report Audit` section and changes nothing else — no severity moves, no findings dropped, no re-ranking. A failed audit prints `Not run (audit agent failed).` and the report goes out regardless; withholding a real review over a failed advisory check is the worse trade.
- **Independent of `--adversarial` in both directions.** It runs on an unrefuted report (two of its seven failure classes do not apply), and enabling refutation does not enable it.

**Loop defaults (looping `pr` target only):**

- **`--max-iterations`**: **1**, lowered from 3. Hard ceiling is **8** — refuse anything higher (a `--max-iterations 50` request indicates a misunderstanding of the loop's purpose). The old default assumed rounds converge. Measured across 10 real loop runs (`${CLAUDE_PLUGIN_ROOT}/skills/zord-multi-agent-review/scripts/loop_metrics.py`, run against the persisted round artifacts of two zord-baton-runner campaigns): **0% of findings carried from one round to the next** while 22–56% of the *files* overlapped, and 8 of 10 runs scored `RANDOM_WALK` with none scoring `CONVERGING`. Same code, a fresh set of complaints each round. Extra rounds over a loop that does not converge buy noise and cost, not follow-ons. Raise this default again only against a run where `loop_metrics.py` shows carry-forward rising and blocking findings falling.

  **The obvious repair was measured and rejected.** Carrying each round's fixed/deferred findings into the next round's prelude, so stateless reviewers stop rediscovering them, made reviews *worse* at two executor tiers: see `ThinkTime/versus/fixtures/review-round2-carryforward/README.md` in the `z0rd0n88/ThinkTime` repo (moved there by ClaudesMods#187). Naming a finding in a "do not re-raise" list appears to make it more salient, not less. Do not re-attempt that design without measuring it.

  **What replaced it — carrying structure rather than finding text — does work, on capable executors.** Measured against `ThinkTime/versus/fixtures/review-round2-lens-rotation` (v3, N=9): on the class-hunt assertions the rotation arm found defects the previous lens structurally could not reach in **25 of 36** observations against the baseline's **4 of 36** (Fisher exact p ≈ 1e-6; p = 0.00016 under the conservative collapse of the two same-file assertions). Precision guards held — no scope leak, no blindfolding, no decoy false positives. **This does not lower `--max-iterations`' default back down**: rotation makes an *extra* round find different things, it does not make findings converge, and carry rate is still not the success metric.

  **It buys nothing on a weak executor, and it is not free.** At the cheaper tier *both* arms scored 0 of 36 on those same assertions — that model does not hunt a defect class outside the diff whatever it is told, so the instruction is pure cost there. Rotation reads more files every round: tool calls lost 7–0 (p=0.0078) at the capable tier and cost lost 8–0 (p=0.0039) at the cheap one. Prefer it where the roster runs on a capable model; it is a poor trade on a cheap one.
- **Round state is carried forward as structure, never as finding text (§10.2 step 0).** Reviewers are stateless, so absent this the loop redraws from the same sample space every round: it rediscovers whatever the first lens was good at and stays blind to everything that lens structurally could not see. Two carriers, both subtractive, and **neither names a finding** — a suppression list that names a defect makes that defect *more* salient, not less (measured; see `ThinkTime/versus/fixtures/review-round2-carryforward/README.md`).

  - `roundShapes` — the review shape each prior round ran: the reviewer roster, and which axes it actually read (code, specs and docs, tests, config, history). Round N+1 **must rotate to a shape no earlier round ran**, and must state in its report which shape it used. Rotation is not a reshuffle of the same roster. Prefer, in order: (a) **merging two axes that previously ran separately**, so a claim made on one can be checked against the other — a defect that is only visible as a *contradiction between* two sources is invisible to every lens that reads one of them alone; (b) **hunting by defect class rather than by instance** — a fix applied at one site is a hypothesis that the same class exists at that site's analogues, and re-checking only the site that was fixed cannot test it.

  - `verifiedFixed` — the set of individual **findings** a §10.4b verifier positively confirmed, each carrying its `symbol`, `file`, a one-line `finding` description, and the verifier's evidence. **This is the only subtraction the loop is permitted to make, and it is scoped to the exact finding, never to the whole symbol it sits in.** A finding matching a `VERIFIED-FIXED` entry is out of scope for later rounds; raising it again is a scope leak, not diligence. A *different* finding in the same function or class stays fully in scope — verification confirms one claim, not every invariant its enclosing symbol carries. **Each entry is bound to the `blob` hash of the file it was verified against, and the subtraction expires when that file changes:** the renderer then lists it under `### Re-verify (file changed since verification)` and the exact finding is back in scope, because a later round's fix can reintroduce the defect an earlier round closed. **An exclusion also survives only within the commit it was settled on:** a blob binds one cited file, while a finding can be revived by a change to a file it never cites, so any new commit reopens every settled entry — verified and refuted alike — for re-verification. Everything else stays in scope **regardless of whether an earlier round touched it** — "round N edited this" is not evidence the defect is gone, and treating an unverified edit as settled is the blindfold that lets a loop reach APPROVE over code nothing actually checked. Absent a verifier run the set is empty and nothing is subtracted.

  Both carriers live in `<git-root>/.claude/reviews/pr-<n>/loop-state.json`, written by the coordinator at the end of every round and rendered into the next round's `--prompt-prelude` by `${CLAUDE_PLUGIN_ROOT}/skills/zord-multi-agent-review/scripts/loop_state.py` — the only renderer, so the prelude cannot carry finding text by construction. The same file is the loop's resume record: re-running the command on a PR whose state file's recorded head **exactly matches** current `HEAD` continues at the next round instead of starting over (§10.1) — an ancestor relationship isn't enough, because commits landed since the checkpoint can change what a `verifiedFixed` or `refuted` entry still claims is settled. It also carries `prior_findings_fingerprints` (each with whether the finding was claimed fixed), which the coordinator restores before dispatching the resumed round — without it a recurring defect resumes as a brand-new finding and the loop mutates again instead of stopping for a human. A checkpoint that already spent its `max_iterations` checks `COMPLETE`, not `RESUME`: the budget is gone, so another round is a fresh loop, not a resume. A checkpoint left on a `STOPPED_*` safety stop is likewise not auto-resumable — that state exists to get a human's judgment, so resuming past it needs an explicit `--resume-stopped` after that judgment is made. Each `verifiedFixed` / `refuted` entry additionally records a `settled_head`, stamped by `loop_state.py stamp` as the round's last step: `verifiedFixed` binds to the post-commit `HEAD` (the verifier ran after the fix), `refuted` to the round-start commit its refuters actually read, so a fix landed later in the same round reopens the claim instead of shipping it as settled. The renderer reopens either entry once `HEAD` is any other commit: the checkpoint's global `head` is rewritten every round, so only a per-entry binding stops a round-1 exclusion surviving a round-2 commit to an uncited caller, middleware, or config that invalidated its proof.

  Carried state is scope, never an answer. It fixes which shape the round uses and which symbols are already settled; it never tells a reviewer what to find, and it never suppresses by naming. The success measure is whether the rotated round finds defects the previous shape could not — **not** whether findings repeat: `${CLAUDE_PLUGIN_ROOT}/skills/zord-multi-agent-review/scripts/loop_metrics.py`'s carry rate is a diagnostic, and a rotation that raises carry rate without finding new real defects has failed.
- **Action floor**: by default the coordinator MUST address every CRITICAL and HIGH; MEDIUM is coordinator's judgment; LOW is "note in PR comment, do not iterate on." With `--high-and-up-only`, MEDIUM and LOW are auto-deferred without prompting.
- **Smoke test gate**: re-run the project's live smoke ONLY if a fix touched code paths the smoke exercises. The set of smoke-relevant paths is project-specific — typical examples: external-connector loops, request-parse paths, allowlist/permission filters, metric-increment sites, top-level route handlers. Skip the smoke when fixes only touched paths the smoke doesn't cover. `--no-smoke` opts out entirely.
- **`--high-cap` is forced `off` on every inner review pass.** The loop gates iteration on CRITICAL+HIGH findings; the default HIGH-severity budget (`--high-cap` on) would demote surplus HIGHs to MEDIUM, letting the loop reach APPROVE with real HIGHs still outstanding. Forcing the cap off keeps every HIGH visible to the gate. If a caller explicitly passes `--high-cap <n>` on a looping `pr` target, **warn that it is overridden to `off` in loop mode** — don't silently drop it.
- **One-shot flag behavior in loop mode:** the report file is written **once** — the final loop report — not once per round (per-round reviewer transcripts stay in their fresh subagents; the final report is the only *report* persisted — the always-on `.claude/reviews/` checkpoints (§5A.5, §10.3 step 0a) separately keep each round's raw return as recovery artifacts, not reports). This holds for the default path and for `--write-to` alike, and it is enforced structurally: the coordinator **forces `--no-write` on every inner review pass**, the same way it forces `--high-cap off`. Neither `--write-to` nor `--no-write` is ever forwarded — an inner pass that inherited the default would emit one file per round, and one that inherited `--write-to` would overwrite the same path N times. The caller's own `--no-write` still governs the coordinator's final loop report. `--no-comment` is likewise not forwarded: inner passes never comment, and the caller's choice governs the single loop comment in §10.7. `--prompt-prelude`, `--mode`, `--reviewers`, `--synthesizer`, `--adversarial`, `--refuters`, `--max-refuters`, `--no-report-audit` are **forwarded to each inner review pass** (every round runs the same roster/mode/prelude/refutation settings).
- **Refutation is not forced on or off by the loop** — unlike `--high-cap`, which the loop pins to `off`. The caller's choice is forwarded verbatim, and the default (off) is inherited like any other. The reasoning is the mirror image: `--high-cap` is forced `off` because demotion *hides* real HIGHs from the iteration gate, whereas refutation removes findings only after they lose an evidence contest, which is precisely what the gate should be measuring. A loop without `--adversarial` is a supported, louder, cheaper loop — it will apply fixes for findings nothing challenged, which is why the unattended (`--yes`) case emits the recommendation note above.
- **Refuted findings are carried forward as an exclusion list.** A finding dropped in round N must not be re-raised in round N+1 — the reviewers are stateless and will rediscover it every round, burning refuters on the same dead claim and inflating apparent finding counts. The coordinator records dropped findings in `loop-state.json`, and `${CLAUDE_PLUGIN_ROOT}/skills/zord-multi-agent-review/scripts/loop_state.py` renders them into the inner pass's `--prompt-prelude` under a `## REFUTED IN EARLIER ROUNDS — DO NOT RE-RAISE` heading, reusing the existing exclusion-list mechanism (`refs/multi-agent/exclusion-list.md`). **This is the one carrier that names findings.** It has not been measured against the salience effect that sank the fixed/deferred prelude; it is retained because a re-raised dead claim re-spends refuters, but it is the first thing to replace if the loop metrics show refuted claims returning. Each entry carries the refuters' reasoning, so a later round can still raise it *if the diff has changed underneath it* — the carry-forward suppresses repetition, not revision. That expiry is mechanical, not a judgment call: each entry is bound to the `blob` of the file it was refuted against, and once that file changes the renderer moves it to a `RE-EXAMINE` block instead of the exclusion list.
