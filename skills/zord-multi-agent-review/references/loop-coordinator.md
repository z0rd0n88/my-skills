# zord-multi-agent-review — Loop coordinator details

> Reference file for [`../SKILL.md`](../SKILL.md) (zord-multi-agent-review): full review→fix→re-review loop mechanics — per-iteration dispatch, triage, fix application (serial and parallel), fix verification, commit/push, control/stop conditions, final report format.

## 10. Loop coordinator details

The per-round protocol for §5B. The coordinator MUST follow these steps in order each round. (The one-shot skill invoked inside each round is read-only by construction — the fix step lives here, in the coordinator, not in the review subagent.)

### 10.1 Initialize loop state

Create a TodoWrite-style task list — one task per planned iteration plus a final "summarize and close" task — to make progress visible. Initialize:

- `iterationsCompleted = 0`
- `checkpointDir = <git-root>/.claude/reviews/pr-<number>/` — created now (`mkdir -p`). Every round's synthesized return is persisted here the moment it arrives (§10.3 step 0a) and the inner pass writes per-reviewer checkpoints under the same root (§5A.5), so a session that dies mid-loop keeps every completed round on disk. Working artifacts, never staged or committed; §5A.1 step 10 keeps `.claude/reviews/` ignored through `<git-common-dir>/info/exclude` (a checkpoint can name an unfixed vulnerability — same exposure as §4's report-file note).
- `stateFile = checkpointDir/loop-state.json` — the loop's carry-forward and resume record, written at the end of every round (§10.5 step 6) and before any stop (§10.6). **Resume check, before anything else:** run `python3 ${CLAUDE_PLUGIN_ROOT}/skills/zord-multi-agent-review/scripts/loop_state.py check <stateFile> --pr <n> --remote-head <oid>` from the repo, where `<oid>` is `gh pr view <n> --json headRefOid --jq .headRefOid`. Resume requires the checkpoint head, local `HEAD`, and the live PR head to be the **same commit**: this worktree can sit at the checkpoint while another actor force-pushes or fast-forwards the PR branch, and resuming then reviews code the PR no longer has. The script never fetches — pass the OID, keep the check offline. `NONE` → fresh loop. `RESUME round=<k>` → load the file, restore every field below from it, set `iterationsCompleted` from it, and start at round `k`; say so in the first line of output (`resuming PR #<n> at round <k> from <stateFile>`). `STALE <reason>` → rename it to `loop-state.stale-<epoch>.json`, note the reason once, and start fresh — **a fresh loop still has to pass §5.0 step 7's clean-tree and head-parity preconditions before it dispatches anything; STALE is not a licence to skip them** — the check requires the recorded head to **exactly match** current `HEAD`, not merely be an ancestor of it: any commit landed since the checkpoint (a rebase, a human's manual fix, an unrelated merge) can change what a `verifiedFixed` or `refuted` entry claims is settled, and an ancestor check would carry that stale scope forward silently. `COMPLETE <reason>` → either the checkpoint already spent its `max_iterations` or it carries `status: "approved"` (§10.3 step 1's terminal APPROVE); there is no round to resume, so either accept the loop as finished or start a fresh loop with a new budget. A `STALE working tree or index is dirty` is the one STALE that is not about commits: every head can match while an interrupted round left an applier's edits uncommitted, and resuming would sweep them into the next finding's commit — inspect and commit or discard them by hand, then start fresh. `STOPPED <reason>` → the loop's last round ended on a safety stop (§10.6), not an interruption — **do not resume automatically.** Treat it the same as a fresh loop's confirmation gate: surface `<reason>` to the human and only pass `--resume-stopped` to the check after they judge it safe to continue past that specific stop; absent that judgment, start a fresh loop instead. `--resume-stopped` is a public looping-`pr` flag (SKILL.md `-h` table; `flags.md` §3), validated with the other loop flags, and it goes **only** to `loop_state.py check` — never into a round's inner review pass, an applier brief, or `stateFile`. Schema and the render contract: the script's docstring. Coordinator-only fields (`deferred`, `fix_outcomes`, totals) are stored for resume and **never rendered to a reviewer**; the script enforces that, not the prose.
- `roundShapes = [ {round, roster, axes, filesRead} ]` — the review shape each completed round ran, parsed from its `## Shape` block (§10.2 step 2). Carried forward so round N+1 can rotate away from it (§10.2 step 0).
- `verifiedFixed = [ {symbol, file, finding, evidence, round, blob, settled_head} ]` — every **finding** a §10.4b verifier ruled `FIXED`, `finding` its one-line description from the round report, `evidence` the verifier's `REASON`, `blob` the `git hash-object` of `file` and `settled_head` the `git rev-parse HEAD` — **both written by `${CLAUDE_PLUGIN_ROOT}/skills/zord-multi-agent-review/scripts/loop_state.py stamp`, not by the verifier**: §10.4b records the entry with neither field, and §10.5 step 7 stamps it after the round's commits exist. Stamping at verification time would bind the pre-fix HEAD, and the round's own fix commit would then expire every fix it just landed. **The verification is bound to that blob:** when `file`'s current blob differs (or the entry predates the field), the renderer moves the entry out of the out-of-scope list into a `### Re-verify (file changed since verification)` block and the exact finding is back **in** scope — a later round's fix can reintroduce a defect an earlier round closed, and an unbound entry would tell round 3 not to look. **A new commit reopens the entry regardless of blob, and the test is per entry, not per checkpoint.** A blob binds one cited file, but a finding can be made valid again by a change to a file it never cites — middleware, config, a caller — which leaves the cited blob untouched. Those dependency sets are not knowable here, so the renderer takes the conservative fallback: an entry whose `settled_head` is not current `HEAD` (or which carries none) moves to its re-verify block. The binding must be per entry because §10.5 step 7 rewrites the state's global `head` to the latest post-push commit every round while keeping older entries — comparing against that field alone would let a round-1 exclusion survive into round 3 after a round-2 commit invalidated its proof. An exclusion therefore survives only within the commit it was settled on; blob-matching still governs mutations made *within* that commit. The only subtraction later rounds may make from scope — and it subtracts the exact finding, never the whole `symbol`: verification confirms one claim, not every invariant in the function or class it sits in, so a second, different defect in the same symbol stays fully in scope (§10.4b).
- `findingsFixedThisRun = { CRITICAL: 0, HIGH: 0, MEDIUM: 0, LOW: 0 }`
- `findingsDeferredThisRun = { MEDIUM: [], LOW: [] }` — each entry carries the §10.3 step 4 criterion; persisted in `stateFile` for resume and rendered only in §10.7.
- `priorFindingsFingerprints = Set<string>` (used in §10.6 for regression detection) — **persisted in `stateFile` as `prior_findings_fingerprints = [ {fingerprint, claimed_fixed, round} ]` and restored from it before the resumed round is dispatched.** Without it a resumed loop treats a recurring finding as new and mutates again instead of stopping for a human; a checkpoint written after a completed round that lacks the field is `STALE`, not resumable.
- `refutedFindings = Map<fingerprint, {severity, location, claim, rationale, round, file, blob, settled_head}>` — findings DROPPED by refutation (§10.3 step 3), `file` the path the claim was about, `blob` and `settled_head` its binding — again written by `loop_state.py stamp` at §10.5 step 7, not at refutation time, for the same reason `verifiedFixed` is stamped there. **A refutation binds to the ROUND-START commit, not to the post-fix `HEAD`** (`stamp --round-start <oid>`): the refuters examined the tree as it stood before the round's fixes, so binding them to the final commit would present a claim as disproved against code no refuter read — and a same-round fix can make a previously false claim true. **The exclusion carries both bindings exactly as `verifiedFixed` does:** once `file`'s current blob differs, or `settled_head` is not current `HEAD`, or either is absent, the renderer moves it out of the exclusion list into a `## REFUTATIONS THAT NO LONGER HOLD — RE-EXAMINE` block and the claim is back **in** scope — a later fix can change or reintroduce the behaviour the refuters disproved, and an unbound exclusion would suppress it forever. Two consumers: it is serialized into each subsequent round's exclusion prelude so stateless reviewers stop rediscovering dead claims, and it is rendered in the final report (§10.7) so the human can overrule any drop. Always empty when refutation did not run (no `--adversarial`).
- `refutationTotals = { upheld: 0, contested: 0, dropped: 0, unverified: 0 }` (accumulated across rounds for §10.7)
- `fixOutcomes = Map<fingerprint, {outcome, severity, location, reason, round}>` where `outcome ∈ { FIXED, PARTIAL, FIX_FAILED, REGRESSED }`, and `FIX_FAILED` carries an optional qualifier rendered in the report but never parsed as a distinct outcome — `FIX_FAILED (unverified)`, `FIX_FAILED (partial, unretried further)`, `FIX_FAILED (test modified)`. **Qualifiers narrow the report, never the gate — with one enumerated exception.** §10.3 step 2's re-raise suppression and §10.7's UNRESOLVED renderer match the bare outcome, so an unrecognised qualifier cannot escape them. §10.6's CRITICAL stop is the exception: it fires on `FIX_FAILED` **unless** the qualifier appears in that section's carve-out list (today: `(unverified)` alone, because a failed verifier process says nothing about the code). The default there is fatal, so **introducing a qualifier requires stating its §10.6 disposition.** The per-fix result comes from §10.4/§10.4b. `REGRESSED` and `FIX_FAILED` entries are **unresolved findings that were attempted**, distinct from both "fixed" and "deferred by judgment"; §10.7 renders them in their own section, and §10.3 step 2 reads this map to avoid mistaking their expected re-raise for a regression.
- `fixVerifyTotals = { fixed: 0, partial: 0, notFixed: 0, unverified: 0 }` (accumulated across rounds for §10.7)
- `applierAssignments = Map<fingerprint, {ownedFiles: string[], applier: string, preDispatchPaths: string[], preDispatchBlobs: path, preDispatchTestBlobs: path, preDispatchSha: string, preDispatchStaged: string[], preDispatchUpstream: string, preDispatchRemotes: string, preDispatchRemoteRefs: string}>` — on the §10.4a parallel path the same eight snapshots are recorded **once per batch** rather than per finding (one shared working tree), keyed under the batch rather than a fingerprint. **A retry never overwrites the entry it retries** (§10.4b's `PARTIAL` path): key the second attempt separately and keep attempt 1's snapshot, because the revert prescribed on a failed retry must undo *both* attempts and only attempt 1's blobs describe the pre-fix tree — the per-finding file ownership handed to each applier, **serial (§10.4 step 2) and parallel (§10.4a) alike**, plus the two pre-dispatch snapshots §10.4 step 3 needs to measure that applier's diff *differentially*. Kept for the round because every ownership check — §10.4 step 3's hard boundary and §10.4a step 3's post-batch verification — is a **verification against this map**, not a trust in what the appliers report; an applier's own `FILES:` line is evidence, never the authority. The snapshots are what make that check meaningful (§10.4 step 3).
- `coverageRedispatches = Map<round, count>` (used in §10.3 step 1 — the empty-coverage re-dispatch is once PER ROUND; a later round gets its own single re-dispatch. Mirror each re-dispatch as `redispatched r<N>` / `formatting-failure r<N>` text in the round's TodoWrite item — the visible task list is the durable in-session record a post-compaction coordinator can reread.)

### 10.2 Per-iteration: dispatch the review subagent

For iteration `N = 1, 2, …, maxIterations`:

0. **Build the round prelude from the state file, and validate it — round 2 onward, BEFORE the dispatch in step 1.** Run `python3 ${CLAUDE_PLUGIN_ROOT}/skills/zord-multi-agent-review/scripts/loop_state.py render-prelude <stateFile> --round <N> [--caller-prelude <caller's path>]`, write its stdout to `<checkpointDir>/prelude-round-<N>.md`, **then confirm that file exists and is ≤ 16 KB before constructing the step-1 brief.** The order is load-bearing and is why this is step 0: step 1 blocks on the round subagent, whose inner pass reads the `--prompt-prelude` path the moment it starts. Rendered after the dispatch, that path does not exist yet and round 2 hard-fails (`--prompt-prelude file not found`) before a single reviewer runs — the round is lost, and the coordinator learns only from the failure return. The script refuses (exit 2, nothing written) when the render exceeds the cap, so an over-cap prelude is a mechanical stop here rather than a `--prompt-prelude file is <n>KB` hard-fail inside an already-spawned subagent; on that refusal, drop `files opened` lists oldest-round-first until it fits and re-render — never drop the verifier block. A prelude that cannot be written at all is noted (`prelude-missing r<N>`) and round N runs with the caller's prelude alone (§11).

   The script is the only renderer, and what it renders is **scope, never answers**: the shapes earlier rounds used (`roundShapes`), the `verifiedFixed` set as a verifier-output block, and — only when `--adversarial` ran — the `refutedFindings` exclusion list. It never renders a fixed, deferred, or failed finding, because a prelude that names a finding to suppress it makes that finding *more* salient (measured; `ThinkTime/versus/fixtures/review-round2-carryforward/README.md` in the `z0rd0n88/ThinkTime` repo). Do not append finding text to this file by hand. The rendered block tells the round to **rotate to a shape no earlier round ran** — merging axes that ran separately, or hunting the class of a landed fix at its analogues — and to subtract only `VERIFIED-FIXED` symbols from scope; "round N touched it" subtracts nothing. Both mechanisms measured positive on capable executors (`ThinkTime/versus/fixtures/review-round2-lens-rotation`, §4). Skip this step entirely on round 1 — there is no state to carry yet.

1. Spawn a **fresh general-purpose subagent** via the `Agent` tool, with **`run_in_background: false`** (SKILL.md Hard rule 1). The brief MUST be self-contained — the subagent has no shared context with the coordinator.

   > ⚠️ **This is the single most consequential dispatch in the skill.** It carries an entire review round, and it sits inside `for N = 1..maxIterations`. Backgrounded, the coordinator's turn ends the moment this call is issued: the round's return notifies the top-level session instead of the coordinator, §10.3's triage never runs, no fix is ever applied, and §10.7 renders a final report from empty loop state — a loop that reports completing `maxIterations` rounds having done nothing. Every dispatch in §10 blocks; this one is where it costs the most.

2. The subagent brief MUST include:
   - The repo's worktree path (absolute).
   - The PR number and the branch name.
   - The instruction: `Skill(skill="zord-multi-agent-review", args="pr <pr-ref> --no-loop --in-loop --high-cap off --no-write --no-comment <pass-through review flags>")` — where `<pass-through review flags>` is exactly the caller's `--reviewers`/`--synthesizer`/`--mode`/`--adversarial`/`--refuters`/`--max-refuters`/`--no-report-audit` (never the loop-control flags, never `--high-cap`, and never the caller's `--write-to`/`--no-write`/`--no-comment`), plus **`--prompt-prelude <checkpointDir>/prelude-round-<N>.md` from round 2 onward** — the file step 0 renders, which embeds the caller's own prelude. Round 1 forwards the caller's `--prompt-prelude` unchanged (there is no state to carry yet). Unlike `--high-cap`, the refutation flags are forwarded **verbatim** — the loop neither forces refutation on nor off (§4). When the caller did not pass `--adversarial`, nothing refutation-related is forwarded and every round runs unrefuted.
   - **Hard rule:** "Do NOT apply any fixes. Report-only. The orchestrator session applies fixes."
   - The required output schema:
     ```
     VERDICT: APPROVE | NEEDS_CHANGES | BLOCK

     ## Shape
     - roster: <reviewer names actually dispatched>
     - axes read: <subset of: code, specs-docs, tests, config, history>
     - files opened: <paths the reviewers read beyond the diff, or "diff only">

     ## CRITICAL
     - <file_path>:<line> — finding — fix recommendation

     ## HIGH
     - ...

     ## MEDIUM
     - ...

     ## LOW
     - ...

     ## Refutation
     - upheld: <n> / contested-demoted: <n> / dropped: <n> / unverified: <n>
     - dropped: <for each, `<severity> <file>:<line> — <claim>` + a one-line refuter rationale, so the coordinator can carry it into the next round's exclusion prelude and a human can overrule it>
     - "not run (refutation off; pass --adversarial to enable)" when refutation did not run

     ## Report Audit
     - <each audit item from §5A.6a, one line each, or "clean" / "not run">

     ## Coverage
     - Reviewers: <returned>/<dispatched> returned   # §5A.5's line, copied verbatim including the capital R
     - confirmed: <n> — <the single strongest confirmed claim WITH its citation (file:line + evidence), so the coordinator can spot-check it>
     - examined inconclusive: <n> — <one line: what was traced and the blocker>
     - not examined: <the round's residual-risk list, verbatim from the Coverage Report>
     - severity-using reviewers engaged: <k>/<n> (<names>)
     - non-engaged reviewers: <names tagged [DID NOT ENGAGE], or "none">

     ## Open Questions
     - <every `## Open Questions for the Author` bullet from the synthesized report, verbatim with its `— Disposition:` suffix, or exactly `none raised`>

     ## Notes
     - any reviewer disagreements
     ```
   - **The two failure returns, which replace the schema rather than partially filling it.** The inner one-shot pass has hard-fails of its own — a rostered reviewer still refused after its one re-dispatch (§5A.4), a `returned < dispatched` reconciliation (§5A.5), a parse-time hard-fail (§11) — and every one of them ends with "emit no report". That leaves the round subagent holding an error string and no verdict. It MUST NOT invent one. Return **exactly one line and nothing else**, choosing by cause:

     ```
     DISPATCH-FAILED: <reason>     # the fan-out could not happen at all (Agent tool unavailable — step 3)
     ROUND-FAILED: <reason>        # the inner pass ran and hard-failed; <reason> is its error, verbatim
     ```

     **A round that cannot produce a report has exactly these two ways to say so.** Anything else — a hand-written summary, a partial schema, a verdict the subagent reasoned to itself, "the review could not be completed but here is what I found" — is the failure this whole section exists to prevent, arriving in the one mode that then edits, commits, and pushes. A missing report is recoverable; a fabricated one is not. Do not soften a `ROUND-FAILED` into a `NEEDS_CHANGES` because findings happened to be visible before the hard-fail: those findings came from an incomplete fan-out, which is why the pass refused to synthesize them.
   - The inner self-call's fallback forms — **every form MUST carry the recursion guard.** Primary: `args="pr <n> --no-loop --in-loop --high-cap off --no-write --no-comment <pass-through flags>"`. If that fails to resolve, retry once with the PR URL in place of the number: `args="pr <url> --no-loop --in-loop --high-cap off --no-write --no-comment <pass-through flags>"`. NEVER issue a form without `--no-loop --in-loop --high-cap off --no-write --no-comment` — the base command loops by default, so a bare self-call would recurse, and an inner pass without the artifact suppressors would write one report file per round and comment on the PR every round. If both forms fail, list the inner skill's installed location (e.g. `~/.claude/plugins/.../zord-multi-agent-review/skills/zord-multi-agent-review/SKILL.md`) and stop.

3. **Subagent-dispatch precondition check** — the original of the pattern §5A.0 now extends to the one-shot orchestrator. This round subagent **is** layer 1 of the two-layer contract, which is why its inner call carries `--in-loop` (forcing `inline`, §5.0 step 4): the round must not spawn a second orchestrator between itself and its reviewers. The brief MUST instruct the subagent to verify the `Agent` tool is available in its environment before invoking the inner skill.

   **If it is not, the subagent returns exactly `DISPATCH-FAILED: Agent tool unavailable in subagent context` and nothing else.** The coordinator stops the loop with verdict `STOPPED_DISPATCH_UNAVAILABLE`, reports which round failed, and surfaces to the human. Do not retry — a missing tool does not appear on a second attempt.

   > **The inline fallback that used to live here is withdrawn.** It instructed the subagent to
   > "execute the four reviewer lanes inline (one agent role-playing four), then synthesize",
   > mitigated only by the coordinator "should weight findings from an inline-fallback round
   > less" — a `should`-weighted discount is not a control. §5A.0 calls a single agent role-playing
   > a roster "the exact failure §12 warns about" and refuses it in one-shot mode; loop mode
   > accepted it in a path that then **edits, commits, and pushes**, with zero real subagents run.
   > It also hardcoded *four* lanes while the default roster is six, silently dropping lanes.
   > Refusing here costs a stopped loop; accepting cost commits.

### 10.3 Per-iteration: triage findings

When the subagent returns:

0a. **Persist the round before touching it (R12).** Write the subagent's verbatim return — verdict, findings, coverage block, refutation outcomes, audit block — to `checkpointDir/round-<N>.json` with `{"round", "verdict", "collected_at", "output"}`. This happens before triage, before the gate, before any judgment: the checkpoint's job is to survive whatever the rest of this section decides, including a coordinator that never reaches §10.7. Failure to write is noted once and never stops the round.

0. **The `## Report Audit` block is read, never actioned.** Audit items are statements about the *round report's* fidelity (§5A.6a), not defects in the code, so they **never** enter triage, never become fixes, and never drive iteration — a coordinator that "fixed" an audit item would be editing source in response to a synthesis complaint. Use them only to weight how much to trust the round: an audit reporting unapplied refutation outcomes or a budget-distorted severity is reason to re-read the round's findings before acting, and an audit reporting lost or misattributed findings is reason **not** to treat this round's APPROVE as final. Carry the items verbatim into §10.7's final report so they are visible to a human. If the audit says a HIGH was demoted to fit the cap, treat that as a signal the cap was not correctly forced `off` (§4) and say so in the round note rather than silently re-promoting the finding.

0b. **Round-usability gate — runs on EVERY round, before the verdict is even read.** Two checks, in this order. Both stop the loop; neither is traded off against how many fixes landed in earlier rounds.

   **(i) Is this a round report at all?** Classify the return before parsing it:

   | Return shape | Action |
   |---|---|
   | The §10.2 schema, opening `VERDICT:` | Continue to (ii). |
   | Exactly `DISPATCH-FAILED: <reason>` | Stop: `STOPPED_DISPATCH_UNAVAILABLE`. The fan-out never happened. |
   | Exactly `ROUND-FAILED: <reason>` | Stop: `STOPPED_ROUND_UNUSABLE`, carrying `<reason>` verbatim into §10.7 — it is the inner pass's own error and names which hard-fail fired. |
   | Anything else — prose, a partial schema, a summary, a verdict with no `## Coverage` block | Stop: `STOPPED_ROUND_UNUSABLE`, reason `unparseable round return`. **Do not repair it, do not infer a verdict from it, and do not re-dispatch** — a subagent that returned the wrong shape once has already demonstrated it is not following §10.2, and the coordinator has no way to tell a degraded report from a fabricated one. |

   Persisting happens at step 0a regardless, so a failure return is on disk before any of this runs.

   **(ii) Did the fan-out reconcile?** Read the `Reviewers: <returned>/<dispatched> returned` line from the round's `## Coverage` block. If the two numbers differ, the round lost part of its fan-out: **do NOT accept the round, and do NOT re-dispatch to paper over it.** Stop the loop with `STOPPED_DISPATCH_UNAVAILABLE` and surface to the human, exactly as for an unavailable `Agent` tool — a round that reviewed with four of six lanes is not a thinner round, it is a round whose verdict means something different from what it says. A **missing** `Reviewers:` line also fails — absence fails, never passes — but stops with `STOPPED_ROUND_UNUSABLE`, not `STOPPED_DISPATCH_UNAVAILABLE`. The distinction is diagnostic and matters to whoever reads the stop: a mismatch is evidence the fan-out shrank, whereas absence usually means the round ran an **older installed skill** that predates §5A.5's reconciliation. That is the normal state mid-rollout, since the inner pass resolves to the installed plugin rather than to this working tree, and telling the human "dispatch was unavailable" would send them debugging the wrong thing.

   > **This is deliberately outside the APPROVE branch, and that placement is the whole point.** An APPROVE ends the loop and is read by a human; a NEEDS_CHANGES or BLOCK goes straight to triage, auto-actions every CRITICAL and HIGH, and **edits, commits, and pushes**. Gating only APPROVE would leave the mutating path — the one place in this skill where a wrong finding becomes an irreversible action with no human in between — with no fan-out check at all. A `NEEDS_CHANGES` derived from one of six lanes must not drive commits onto someone's branch.

1. If VERDICT = APPROVE:
   - **Coverage acceptance gate.** Applies only when the roster contains at least one severity-using reviewer — critical-thinking is exempt from `### Validated`, so an exempt-only roster cannot produce confirmed coverage and is not gated (warn loudly when the roster is known at loop start, else on the first round return; on a `--yes` run also mirror the warning into the final report's Notes). An APPROVE whose `## Coverage` block shows zero confirmed claims is an opinion, not a coverage report — do NOT accept it.
     - **Engagement is a ratio, not a zero-check.** Read `k` and `n` from the schema's `severity-using reviewers engaged: <k>/<n>` line (§10.2 step 2) — `n` counts severity-using reviewers only, so `critical-thinking` is excluded from both sides. The gate used to fire only when **every** severity-using reviewer was tagged `[DID NOT ENGAGE]`, which let `1/6` through as a clean APPROVE — one reviewer's opinion accepted as a six-lane review. **Require a strict majority with a floor of two: `k ≥ max(2, floor(n/2) + 1)`, and `k ≥ 1` when `n == 1`.** Below that, treat it exactly as zero confirmed coverage — the re-dispatch path below applies.

       Same arithmetic as §5A.5a step 4's refuter tally, deliberately: `ceil(n/2)` is wrong here because at even `n` it is a tie, not a majority — `3/6` would pass as an engaged round, and a tied roster is exactly the ambiguous case the gate exists to reject. At `n = 1` the floor of two cannot be met, so that case is carved out and requires the single reviewer to engage — nothing gets looser than the old zero-check.

       Both `k` and `n` are self-reported by a subagent the coordinator cannot observe (decision #28's posture holds), and `n` is unverifiable under context-aware selection where the coordinator never learns the roster. The ratio is a floor on the honest path, not proof.
     - **Missing block:** a return with NO `## Coverage` block fails the gate the same way — **absence fails, never passes**. If the return otherwise shows engagement (evidence-bearing findings), treat it as a **formatting failure**: re-dispatch once with a schema reminder, which does NOT consume the round's coverage re-dispatch; note `formatting-failure r<N>` in the round's TodoWrite item. Only a lazy return (zero coverage AND no evidence-bearing findings) consumes the coverage re-dispatch — except that a SECOND consecutive engaged-but-malformed return does consume it (treated as empty coverage, with counts parsed from prose best-effort first): the schema reminder is once, so the fall-through must be defined or the round deadlocks.
     - **Emptiness claims:** a target with genuinely nothing load-bearing is not an excuse for an empty list — reviewers confirm THAT instead ("confirmed: docs-only diff, no executable surface — evidence: file list"). The coordinator cross-checks such a claim against the changed-file list, where "executable surface" includes interpreted artifacts (SKILL.md bodies, hooks, JSON/YAML config — markdown IS code in a skills repo). A contradicted claim is treated as zero confirmed coverage (gate fails); per-reviewer `[DID NOT ENGAGE]` tagging stays with the synthesizer (§8), which holds the attribution the coordinator never sees.
     - **Re-dispatch:** once per round — record `redispatched r<N>` in the round's TodoWrite item and `coverageRedispatches`. The sharpened brief names the unexamined load-bearing paths as a **validated path list only** (checked against the PR's changed-file list; never free-text copied from the Coverage Report). Fallbacks: not-examined list empty, OR non-empty but zero valid paths after validation → use the changed-file list; behavioral (non-path) risks may be carried as verbatim section headings from the synthesized report. The re-dispatch does not increment `iterationsCompleted`; a re-dispatch that returns NEEDS_CHANGES/BLOCK **supersedes the first attempt** — its findings enter triage (steps 2–4) and normal iteration accounting resumes.
     - **Stop:** if the re-dispatch again returns an empty-coverage APPROVE → STOP with verdict `STOPPED_NO_ENGAGEMENT` and surface to the human — same class of human-judgment moment as a regression. When the round's coverage was examined-inconclusive rather than absent (reviewers traced but could not statically confirm), the final report MUST say so — an unconfirmed clean bill and a lazy one are different human decisions.
   - **Open-question gate.** Read the round's `## Open Questions` block (§10.2 step 2). A missing block is a formatting failure handled exactly like a missing `## Coverage` block: re-dispatch once with a schema reminder, and never read absence as `none raised`. Accumulate the entries across rounds, deduplicated by question text. The coordinator may mark a question `ANSWERED by coordinator — <file:line>` only when the tree settles it and the citation is written down; `FILED` and `DECLINED` are the author's calls, never the coordinator's. A question left PENDING does not block the APPROVE — the loop cannot answer for the author — but it blocks merge-readiness: §10.7's `## Open questions` section is mandatory on every verdict, lists every entry with its setter and evidence, and `## Next action` says the PR is not merge-ready while any is PENDING.
   - **Otherwise → persist the round BEFORE branching on its verdict, then break the loop.** Write `stateFile` per §10.5 step 7 with the incremented `iterationsCompleted` and `status: "approved"`, and only then goto §10.7. An accepted APPROVE is terminal, and §10.5 never runs on this path — there are no fixes to commit — so a `break` straight to the report leaves the checkpoint describing the *previous* round. After an earlier mutating round that is worse than stale: a resume reads it as `RESUME round=<the round just approved>` and re-reviews, re-fixes, and re-pushes work this loop already settled. `check()` returns `COMPLETE approved at round <n>` for a checkpoint carrying that status, so the terminal state is read, never inferred. Every non-approving round is already persisted by §10.5 step 7 at the end of its commit-and-push, with `status: "in_progress"`.

2. Compute a fingerprint for every finding: `sha256(file_path + enclosing_symbol + normalized_summary)`, where `enclosing_symbol` is the function, class, or heading the cited line sits inside (fall back to the file's basename on a target with no symbol structure — plain config, data, or prose files), and `normalized_summary` is the one-line summary lowercased with whitespace and punctuation collapsed.

   **Line numbers are deliberately excluded from the hash.** Any fix that edits *above* a finding shifts that finding's line, so a line-bearing fingerprint changes and the re-raise this step exists to catch is silently missed — the check fails exactly when the round did the most editing. Keep the line alongside the fingerprint for display; never inside it.

   If the same fingerprint appeared in `priorFindingsFingerprints` AND the prior round claimed it was fixed → STOP the loop and emit the "regression detected" report (§10.6). Either the fix didn't land or the reviewer is mis-flagging; either way it's a human-judgment moment, not a coordinator-fixable one. **A finding whose fix was reverted in §10.4 (`REGRESSED` / `FIX_FAILED`) was never claimed fixed**, so its re-raise next round is expected and is not a regression — it re-enters triage normally.

3. **Apply the round's refutation outcomes before partitioning.** The round subagent's `## Refutation` block is authoritative:
   - **DROPPED findings never enter triage.** They are not fixed, not deferred, not commented — they lost an evidence contest. Append each to `refutedFindings`; §10.2 step 0 renders them into the next round's prelude from `stateFile` under `## REFUTED IN EARLIER ROUNDS — DO NOT RE-RAISE` (§4) — never append them to a prelude by hand. A coordinator that "fixes it anyway to be safe" defeats the entire stage and edits the PR on a claim three lenses disproved.
   - **CONTESTED findings enter triage at their demoted severity**, not their filed one. A contested HIGH is a MEDIUM here — it goes to coordinator judgment, not auto-action.
   - **UNVERIFIED findings enter triage at full severity.** Budget exhaustion is not exoneration; treat them exactly as an unrefuted run would.
   - Fingerprint DROPPED findings too (step 2's scheme) and keep them in the refuted-set. If a fingerprint that was dropped in an earlier round comes back **upheld** in a later one, do not treat it as a regression — the diff changed underneath it. Fix it, and note the reversal in the final report; a claim that was false against round 1's code can be true against round 3's.

4. Otherwise, partition the surviving findings:
   - **Auto-action**: every CRITICAL and HIGH.
   - **Coordinator judgment**: every MEDIUM. The coordinator decides per-finding whether to fix or defer based on (a) whether the fix is small (< ~20 LOC), (b) whether the fix risks regressions, (c) whether the finding actually applies to this PR vs. is a pre-existing pattern smell. **Record which criterion drove each deferral** — §10.7's deferred list renders it, and a deferral with no stated reason is indistinguishable from an oversight. Default for `--high-and-up-only`: auto-defer all MEDIUM (reason: `--high-and-up-only`).
   - **Defer to comment**: every LOW. Never iterate on LOW.

5. Add new finding fingerprints to `priorFindingsFingerprints`, and append the round's `## Shape` block to `roundShapes` as `{round, roster, axes, filesRead}`. A missing `## Shape` block is a formatting failure handled like a missing `## Coverage` block (step 1), except that it never fails the gate: record `{round, roster: unknown, axes: unknown}` and note `shape-missing r<N>` — a later round still rotates against "unknown" by stating its own shape explicitly.

### 10.4 Per-iteration: apply fixes

Fixes are applied **one finding at a time, each with its own checkpoint.** The round-level shape — edit everything, then test, then revert everything on failure — is deliberately not used: it discards good fixes to punish one bad one, and it destroys the attribution needed to know which fix regressed.

For each finding the coordinator decided to fix, in descending severity order (CRITICAL → HIGH → MEDIUM):

1. **Write the failing test first — mandatory for CRITICAL, expected for HIGH.** Add a test that reproduces the finding and fails against current `HEAD`, and confirm it fails *for the reason the finding names* rather than for a setup error. A CRITICAL whose fix cannot be expressed as a failing test is a signal the finding is under-specified: say so in the round note and route it to coordinator judgment instead of editing blind. MEDIUM does not require a test. The test is also the durable regression anchor §10.3 step 2's fingerprint can only approximate — it survives line shifts, refactors, and reviewer rewording.
2. **Snapshot repository state, write the fix spec, THEN apply the edit — dispatching a fix-applier only when a language specialist resolves (decision #81).** These happen in that order inside this step, and the order is load-bearing.

   **2a. Take the pre-dispatch snapshot — before the Agent call, not after the applier returns.** Record everything step 3 compares against: `preDispatchPaths`, `preDispatchSha`, `preDispatchStaged`, `preDispatchUpstream`, `preDispatchRemotes`, `preDispatchRemoteRefs`, `preDispatchBlobs`, `preDispatchTestBlobs` (all defined in step 3). **Step 3 is written as a post-return check and numbered accordingly, so its baselines must be captured here, one step earlier.** A coordinator that dispatches first and reads step 3's "immediately before dispatching" bullet only afterwards compares a post-dispatch read against another post-dispatch read: every repository-state assertion, the differential scope guard, and the content-based test-tamper check all pass vacuously, collapsing #76/#77 back to "trust the applier" on exactly the `--yes`-eligible CRITICAL path #71 argues is safe *because* these controls exist. **There is no recovery** — a mutating applier cannot be re-dispatched to retake a baseline. If you reach step 3 and find no snapshot was taken, treat this fix as unverifiable: restore nothing, record `FIX_FAILED (unverified)`, and re-apply it by hand with the coordinator's own `Edit`/`Write`.

   **Snapshot lifecycle on a retry — never overwrite.** §10.4b's `PARTIAL` path re-runs steps 2–4 for a fingerprint that already has a `preDispatch*` set. **Attempt 1's set stays authoritative and is not replaced.** It alone describes the tree as it was before *any* attempt on this finding, and the revert prescribed when the retry also fails must undo both attempts; re-snapshotting first makes attempt 1's edits the new baseline, so the revert silently under-reverts and leaves them in the tree to be committed by §10.5 under the next finding. A retry may record an **auxiliary** set, keyed separately, for scope measurement of attempt 2 only — never as the revert baseline. Equivalent and simpler if you prefer it: make the retry's first action a restore from attempt 1's `preDispatchBlobs`, so attempt 2 genuinely starts where attempt 1 did.

   **2b. Write the fix spec** for this finding (§10.4a step 1 — the judgment that never moves).

   **2c. Resolve the applier — and dispatch only if a language specialist resolves.** Match the file against the same agent union as §5A.1 step 8 (e.g. `kotlin-specialist` for `.kt`); the union is `.claude/agents/*.md` ∪ `~/.claude/agents/*.md`.

   - **No specialist resolves → the coordinator applies this fix itself** with `Edit`/`Write`, and steps 3–4 run unchanged against its own edit. **Do not fall back to `general-purpose` on this serial path** (decision #81). Delegation here was justified by one thing only — a specialist writing more idiomatic code than the coordinator transcribing. With no specialist that benefit is zero, and what is left is a same-model agent holding strictly less context, bought at the price of a fix spec written to be self-contained plus the whole of step 3's repository-state apparatus to police a risk the coordinator never had to take. On a setup that parks its roster (agents in `agents-parked/`, `~/.claude/agents/` deliberately empty) **no specialist ever resolves**, so coordinator-applied is the common path there, not the exception.
   - **A specialist resolves → dispatch** **one** applier with `run_in_background: false`, `subagent_type` = that specialist. `description` = `"Apply fix: <severity> <file>:<line>"`; `prompt` = the expanded [fix-applier brief](agent-briefs.md#7e-fix-applier-brief-template) (§7e). Six rules govern that dispatch:

     1. **The brief carries the failing test on this path.** It includes step 1's failing test verbatim (`{{FAILING_TEST}}`) for CRITICAL and HIGH, so the applier can run it itself before returning — not as a substitute for step 4's checkpoint, but so it doesn't return a plausible-looking edit that never made the test pass. **The block is a property of the serial cadence, not of the severity** (decision #75): §10.4a strips it from every brief in a parallel batch, including a batched HIGH, because a test run in a shared tree reads other appliers' half-written edits.
     2. **The applier edits and nothing else.** The coordinator still owns steps 3–4, run immediately after it returns, so each fix passes its own test checkpoint before the next applier is dispatched. §10.4b's per-fix verification then runs on every survivor, as one parallel pass after the fix step, exactly as it does for coordinator-applied fixes.
     3. **Fallbacks, in order:** a spec the coordinator cannot write without re-reading half the module means the finding is not mechanical — apply it by hand; an applier that returns `APPLIED: no`, fails, or edits outside its owned set (revert its edits wholesale per step 3's hard boundary, note `scope violation` in the round note) → the coordinator applies this one fix itself with `Edit`/`Write`.
     4. **A refusal downgrades the finding to coordinator-applied, never to skipped.** Only a spec the *coordinator* also cannot implement becomes `FIX_FAILED`.
     5. **Step 1's test path is never in `{{OWNED_FILES}}`** — the applier is handed the test as a criterion, not as material, and §7e's immutability rule forbids editing it regardless. **That exclusion does NOT enforce itself, and the path-based guard cannot cover it:** step 1 writes the test *before* the snapshot, so an existing test file is already in `preDispatchPaths` and gets subtracted out of the differential set, while a newly created one is untracked and absent from `git diff --name-only` on both sides. Either way tampering is invisible to a path comparison. Enforcement is therefore **content-based** — step 3's `preDispatchTestBlobs` byte comparison — and that is the only thing standing between a delegated CRITICAL and an applier that weakens its own gate.
     6. **CRITICAL delegation is allowed but held to a stricter verification bar** — see §10.4b's severity split (decision #71). Step 1's failing test, mandatory for CRITICAL, gives the applier the one thing that makes an edit objectively checkable rather than a judgment call. A registered agent's frontmatter `tools:` *is* harness-enforced, so this branch is genuinely narrower than the coordinator's own unrestricted edit — but step 3's repository-state check still runs in full, because a specialist is trusted for idiom, not for scope, and the confused-deputy path (attacker-authored content in the diff it is reading) is unaffected by which agent holds the editor.

   **Why this gate is on the serial path only.** §10.4a keeps its `general-purpose` fallback deliberately: a parallel batch is licensed by *concurrency* on a 4+-finding round, and concurrency does not care who holds the editor, so the fallback still buys what the batch exists for. Serial delegation had no such second benefit. Gate on what each cadence actually buys, not on a uniform rule about appliers.
3. **Diff-scope guard — two boundaries, two verdicts, measured differentially.**

   **Measure this fix, not the round.** Nothing is committed until §10.5, which runs after §10.4b — so during the serial loop the working tree accumulates every earlier finding's edits, and a bare `git diff --name-only` at finding N returns the union of findings 1..N. Compared against finding N's owned set, every earlier finding's path reads as out-of-bounds: a spurious scope violation on a blameless applier, whose prescribed remedy then reverts fixes that already passed their own checkpoints. The measurement must therefore be differential:

   - **These are the definitions; the capture itself happens back in step 2a, before the dispatch.** Record `preDispatchPaths = git diff --name-only`, `preDispatchSha = git rev-parse HEAD`, `preDispatchStaged = git diff --cached --name-only`, `preDispatchUpstream = git rev-parse @{upstream} 2>/dev/null || echo NONE`, the byte contents of **`ownedFiles ∪ preDispatchPaths`** into a scratch dir outside the repo as `preDispatchBlobs`, and — **independently of ownership** — the step-1 test file plus every fixture/helper it reads as `preDispatchTestBlobs`. All six go in `applierAssignments` under this finding's fingerprint (§10.1). `preDispatchUpstream` is captured per dispatch, not once at loop start, so an unrelated `git fetch` elsewhere in the round cannot produce a false stop.
   - **Why `preDispatchBlobs` spans `ownedFiles ∪ preDispatchPaths`, not just the owned set:** the reversion this machinery promises is "owned paths **plus the out-of-bounds paths**," and an out-of-bounds path is by definition not owned — snapshotting only owned files leaves the prescribed revert unimplementable for the exact violation the guard exists to catch, while `git checkout -- <paths>` is banned everywhere else in this section. The union closes that. **Narrow carve-out for the remaining case:** a path that was *clean at snapshot time* (identical to `HEAD`, i.e. absent from `preDispatchPaths`) and is therefore in neither set may be reverted with `git checkout -- <path>` — lossless by construction there, because there were no earlier hunks in it to discard. That is the only permitted use of `git checkout --` in this skill. **Create-then-revert:** restoring a path whose snapshot has no pre-image (the applier created it) means **delete the file**, never a no-op.

   **Repository-state check, before the scope comparison — the applier's "do NOT run git" is a request, not a control.** §5's own note says the skill's `allowed-tools` governs the orchestrator, not dispatched appliers. On the §10.4a batch path `general-purpose` is still the usual `subagent_type` and carries `Bash`, so nothing in the harness stops a batch member from staging, committing, or pushing. On the serial path #81 narrows the executor to a *registered* specialist, whose frontmatter `tools:` **is** harness-enforced — but that is a per-roster fact this skill cannot verify at runtime, and specialists are commonly granted `Bash` anyway, which puts them in the same position. Either way the exposure survives model error and, more importantly, attacker-authored content in the diff the applier is reading (the confused-deputy path, and the reason this matters more now that CRITICAL is delegated under `--yes`). **The check is therefore mandatory on every *dispatched* fix in both cadences, and is never relaxed on account of which applier was chosen** — #81 changes who edits, not what is verified. Read "which agent" as *which applier*, never as "whether an applier was used at all": on a fix the coordinator applied itself (§10.4 step 2c's no-specialist branch) the check has no subject — there is no applier to have run git, no owned set to compare against, and the coordinator is the component that legitimately owns git in §10.5. Skipping it there is not a relaxation; asserting it would be asserting the coordinator against itself.

   **Evaluate all four unconditionally and combine the verdicts, fatal wins — never short-circuit.** Each reads independent state, and one firing does not make the others moot; short-circuiting would permanently shadow the loop-fatal push check behind the commit check, since you cannot push without first committing.
   - **HEAD:** `git rev-parse HEAD` **==** `preDispatchSha`. If it moved, the applier committed. First measure the damage — `git diff --name-only preDispatchSha <moved-HEAD>`; if that set exceeds the owned set this is a containment breach, **stop the loop with `STOPPED_APPLIER_ESCAPED_SCOPE`** (§10.6), not a routine scope violation. Otherwise `git reset --mixed preDispatchSha` — **`--mixed`, never `--soft`**: `--soft` leaves every committed path staged, including paths with no `preDispatchBlobs` snapshot, and §10.5 step 2 commits the *index*, so that content would ship inside the next finding's commit under a message that never mentions it. Then restore `preDispatchBlobs`, record `scope violation (committed)`, and fall back to the coordinator's own edit.
   - **Index:** `git diff --cached --name-only` **==** `preDispatchStaged`. If it grew, the applier staged. Unstage the additions: a staged edit is invisible to a working-tree comparison and would otherwise be committed by §10.5 as part of the next finding. This runs even when the HEAD check already fired, and covers any residual staged content its recovery left behind.
   - **Remote reachability — three reads, not one.** A push is the one violation with no local remedy, so the detector must not be narrower than the act it models.
     - `git rev-parse @{upstream} 2>/dev/null || echo NONE` **==** `preDispatchUpstream`. Both sides use the same `NONE` sentinel, so a branch with no upstream compares equal rather than erroring (`git rev-parse @{upstream}` exits non-zero with a fatal error when none exists).
     - `git for-each-ref refs/remotes` **==** `preDispatchRemoteRefs`, and `git remote -v` **==** `preDispatchRemotes`.

     **The upstream check alone is evadable and must never be the only one.** It watches the branch's configured tracking ref and nothing else, so `git push origin HEAD:some-other-branch`, or `git remote add x <url> && git push x HEAD:leak`, moves no upstream ref and passes. Worse, the local commit those require *does* trip the HEAD assertion, and if the committed diff stayed inside the owned set the spec would route an exfiltration to the **recoverable** branch and call it a routine scope note. Any of the three differing → **stop the loop** with `STOPPED_APPLIER_PUSHED` (§10.6), independently of whether the accompanying commit stayed in scope.

     **Known false positive, accepted deliberately:** a benign `git fetch`/`pull` from an editor daemon, hook, or another session inside the dispatch window advances `refs/remotes/*` and fires this stop. That is the intended trade — the check is cheap and the stop is recoverable by a human re-run, whereas a missed push is not recoverable at all. Record the observed ref delta in the stop's report line so a human can tell a fetch from a push in one look.
   - **Step-1 test:** the test file and its fixtures/helpers must be **byte-identical to `preDispatchTestBlobs`**. A content comparison, deliberately not a path comparison — the hard boundary below cannot serve here, because it is defined over the differential set and the test can never be in it (§10.4b). **Verdict, inline — this assertion is not merely a pointer:** on any mismatch, (1) **restore the test and its fixtures from `preDispatchTestBlobs` immediately**, (2) **skip step 4's checkpoint for this finding — do NOT run the tampered test**, (3) revert the fix per the hard boundary's mechanism, and (4) record `FIX_FAILED (test modified)`. §10.4b's pre-check is the same rule stated where the verifier would otherwise be dispatched; whichever fires first, restoration is mandatory and happens before anything else.

     **Restoration is not optional and not deferrable.** `preDispatchTestBlobs` exists to repair, not only to detect. A weakened test left in the tree becomes the *next* finding's snapshot baseline, laundering the tampering into the round; and §10.5 `git add`s "that finding's paths plus its step-1 test", so a later serial finding sharing that file commits and pushes the weakened assertion. Detection without restoration does not meet the bar this control is claimed to meet.

   Run all of these even when the scope comparison would pass. A well-behaved diff says nothing about whether the index, the branch, or the test moved.
   - After the applier returns, this fix's touched set is `git diff --name-only` **minus `preDispatchPaths`** — never the raw diff. Only that difference is compared against either boundary below.

   **Hard boundary (applier-applied fixes only): the owned file set** from the fix spec — which the coordinator may deliberately draw wider than the cited set (a caller that must change, a test file). A file in the differential set but outside the *owned* set is a scope violation: revert that applier's edits wholesale (owned paths plus the out-of-bounds paths — the reversion §7e promises), note `scope violation` in the round note, and fall back to the coordinator's own edit per step 2.

   **Revert by restoring `preDispatchBlobs`, not with `git checkout -- <paths>`.** A checkout restores a path to `HEAD`, which on the serial path discards every earlier finding's hunks in that same file along with the violating one — and shared files are exactly what the serial path exists to handle, since §10.4a precondition 2 routes every overlapping finding here. `git stash push -- <paths>` fails the same way for the same reason: its unit is the path, not the hunk. Restoring the pre-dispatch blobs subtracts precisely this applier's changes and nothing else. The same restore is what step 4's per-finding revert uses.

   **Soft boundary (every fix): the finding's cited file set.** Any file in the differential set outside it — including owned-but-uncited files — is recorded as `scope-expansion: <finding> touched <extra paths>` with a one-line justification from the coordinator. The soft boundary is a **flag, not a block** — a legitimate fix sometimes has to update a caller — but an unexplained expansion is how a review fix becomes an unrelated refactor nobody reviewed.
4. **Test at the checkpoint.** Run the affected module's tests (read the project's CLAUDE.md for the command — e.g. `pytest path/to/module`, `./gradlew :module:test`, `npm test -- path/to/module`) plus the new test from step 1.
   - **Pass** → record the fix as a commit candidate and continue to the next finding.
   - **Fail** → revert **only this finding's changes** by restoring step 3's `preDispatchBlobs` (not `git checkout -- <paths>`, which would also discard earlier findings' hunks in a shared file — see step 3), record the outcome as `REGRESSED` with the failing output, and continue with the remaining findings. **Do not revert the round.**
5. **Batching is a latency optimization, never a reversion scope — and it lives only in §10.4a.** The serial path never batches: step 2's cadence (one applier, then that fix's checkpoint, then the next) is the invariant, and the only group-apply-and-test-once route is the parallel batch, whose preconditions (≥4 findings, disjoint files, disjoint test modules, no CRITICAL) are exactly the conditions under which a shared test run can be attributed at all. On a union-test failure the batch is re-applied per finding to attribute the regression; the revert is always per-finding.
6. **Smoke gate — once per round, after the last fix.** If any surviving fix touched code paths the live smoke covers AND `--no-smoke` is not set → run the smoke. A smoke failure reverts **every surviving fix that touched a smoke-covered path** and records each as `REGRESSED`; fixes that touched no smoke-covered path are unaffected.
7. **Regenerate auto-maintained docs** if any tracked file was added or renamed (e.g. an `ARCH.md` generator wired into a pre-commit hook). Check the project's CLAUDE.md for the regen command.

#### 10.4a Parallel fix application (conditional)

**Decision #21 is right about triage and overbroad about application.** Deciding *which* MEDIUM applies to this PR, which the author would push back on, and what the fix should be requires project context a sub-fixer does not have. Mechanically editing an already-triaged, already-specified fix into a file nobody else is touching does not. The coordinator therefore keeps the judgment and writes the spec, and **appliers execute it in both paths**: serially, one at a time with a checkpoint between (§10.4 step 2); or — when the preconditions below hold — concurrently as the batch this section defines. **These preconditions gate *concurrency*, not delegation.** They exist because of shared-working-tree hazards (overlapping edits, un-attributable union tests); a single applier in an otherwise-quiet tree has none of those hazards, which is why the serial path dispatches unconditionally for every severity, CRITICAL included (decision #71) — only the *batch* keeps a CRITICAL exclusion, and on different grounds (precondition 4 below).

The split is safe only because §10.4b's per-fix verifier reads the finding and the resulting diff.

**Preconditions — ALL must hold, or the round applies serially per §10.4 (which dispatches one applier per finding at every severity *when a language specialist resolves*, and is coordinator-applied otherwise — serial is a cadence, not a different executor).** The coordinator evaluates these itself; an applier is never asked to confirm its own eligibility.

1. **≥ 4 findings** to fix this round. Below that, the parallel batch saves little wall-clock over §10.4's serial per-finding dispatch, and the per-finding checkpoint it gives up is worth more.
2. **Pairwise-disjoint cited file sets**, computed by the coordinator from the findings. Any pair that overlaps sends *both* findings to the serial group — never to two appliers.
3. **No shared test module.** Two findings needing new tests in the same test file collide even when their source files don't; test files are the most common hidden overlap.
4. **No CRITICAL in the batch.** Not because a CRITICAL can't be delegated — §10.4 step 2 now delegates it like any other severity — but because the parallel batch's whole safety case rests on §10.4b's per-fix verifier catching a bad applier edit before it ships, and decision #71 holds CRITICAL's verifier to a stricter bar specifically *because* it runs without the round-level attribution a serial checkpoint gives. Folding a CRITICAL into a batch would pair the stage that most needs unambiguous attribution with the one that has none (§10.4a step 4's union test can't say which fix broke it). CRITICAL is therefore always applied via the serial path (§10.4 step 2), one applier, one immediate checkpoint — never through the union-tested batch.

**Step 1 — Write a fix spec per finding (coordinator; this is the part that must not move).** For each eligible finding:

- the finding verbatim (severity, `file:line`, description, suggested fix);
- the **exact file set this applier owns** — it may edit these and nothing else;
- the intended change in prose, at the level of "what must be true after," not a patch to transcribe;
- what must **not** change — adjacent patterns that are deliberate, callers that must keep their signature, project conventions the applier cannot infer from the file alone.

A spec the coordinator cannot write without re-reading half the module is a signal the finding is not mechanical: pull it back into the serial group.

**Step 2 — Snapshot the batch, THEN dispatch.** Same 2a-before-2b structure as §10.4 step 2, for the same reason and with the same absence of a recovery path.

**2a. Take the batch-level snapshot — before the Agent calls, not after the appliers return.** All N appliers share one tree, so one shared snapshot covers the batch: record `preDispatchPaths`, `preDispatchSha`, `preDispatchStaged`, `preDispatchUpstream`, `preDispatchRemotes`, `preDispatchRemoteRefs`, `preDispatchTestBlobs`, and `preDispatchBlobs` over **(the union of all assigned file sets) ∪ `preDispatchPaths`**, exactly as §10.4 step 3 defines each — the same widening, for the same reason: a file *no applier owned* is the batch's characteristic violation, and a snapshot scoped to assigned files alone cannot restore it. **This path needs them at least as much as the serial one:** rounds are routinely mixed — precondition 2 sends overlapping pairs to the serial group and precondition 4 sends every CRITICAL there, so the serial group's uncommitted edits sit in `git diff --name-only` owned by no batch applier — and the batch runs *more* concurrently `Bash`-armed appliers than the serial cadence ever does. **A snapshot taken after dispatch is worthless, not merely late:** step 3 then compares a post-dispatch read against another post-dispatch read, every assertion passes vacuously, and `STOPPED_APPLIER_PUSHED` / `STOPPED_APPLIER_ESCAPED_SCOPE` become unreachable on the higher-applier-count cadence. There is no recovery — mutating appliers cannot be re-dispatched to retake a baseline. If you reach step 3 with no batch snapshot, treat the whole batch as unverifiable: re-apply every finding in it serially per §10.4, from a fresh snapshot.

**2b. Dispatch appliers in parallel**, one message, **every call with `run_in_background: false`** — same discipline as §5A.4, which means both halves of it: one message for parallelism, the flag for blocking. `subagent_type` = a language specialist matching the file when one resolves, **else `general-purpose` — the parallel path keeps the fallback that §10.4 step 2 drops** (decision #81): a batch is licensed by concurrency on a 4+-finding round, which does not depend on who holds the editor, whereas serial delegation was justified by idiom alone. Step 3's repository-state check is what makes the broad-tool fallback tolerable here, and it runs on every batch member; `description` = `"Apply fix: <severity> <file>:<line>"`; `prompt` = the expanded [fix-applier brief](agent-briefs.md#7e-fix-applier-brief-template) (§7e).

**Strip `{{FAILING_TEST}}` from every brief in the batch, at every severity** (decision #75). Step 1 above produces no test value — its four bullets are the spec, and none of them is a test — so the variable is undefined here in any case. More importantly it *must* stay undefined: a batched applier running a test observes the union of every other applier's in-flight, half-written edits, so it can pass on broken code or fail on correct code. The `{{FAILING_TEST}}` block is a **serial-cadence** affordance (§10.4 step 2), not a CRITICAL/HIGH one; precondition 4 keeps CRITICAL out of the batch entirely, but **HIGH is batchable**, and a batched HIGH is exactly the case where reading the block's audience as "CRITICAL/HIGH" would hand out a test that must not be run.

**Appliers edit and nothing else.** No tests, no `git` of any kind, no commits, no reading the other findings. This is soundness, not tidiness: all appliers share **one working tree**, so a test run by one proves nothing about the fix that ran it. Testing is the coordinator's, serially, after every applier has returned.

**Step 3 — Verify ownership, don't trust it. Measured differentially, and behind the same repository-state assertions as the serial path.**

**The batch snapshot was taken back in step 2a**, before dispatch — this step only consumes it. Field definitions are §10.4 step 3's; the batch records one shared set rather than one per finding.

**Repository-state assertions, before the ownership comparison.** Run §10.4 step 3's four checks against the batch snapshot, all four unconditionally, fatal winning. A **recoverable batch-level violation fails the whole batch back to serial re-application** rather than blaming one applier: a moved HEAD invalidates every in-flight applier's diff-scope measurement at once, and with a shared tree the commit is not attributable to one of them. **Restore the batch `preDispatchBlobs` and `preDispatchTestBlobs` before re-applying serially** — otherwise the serial pass snapshots the corrupted state as its own baseline and launders it. **A push, or a commit exceeding the assigned union, is not recoverable and not a fallback case:** stop the loop (`STOPPED_APPLIER_PUSHED` / `STOPPED_APPLIER_ESCAPED_SCOPE`, §10.6). Batch cadence changes attribution, never containment. A committed change **disappears from `git diff --name-only` entirely**, so without these assertions an applier that commits looks identical to one that made no edit — which the fallback table treats as a benign refusal, sending the coordinator off to reapply by hand while the illicit commit rides along in the history §10.5 pushes.

**Ownership comparison.** The batch's touched set is `git diff --name-only` **minus the batch `preDispatchPaths`** — never the raw diff. Compare that difference against the union of assigned file sets:

- a file **no applier owned** → some applier went out of bounds;
- a file touched by an applier that **didn't own it** (attributable when ownership sets are disjoint) → the same;
- either case → revert that applier's finding by restoring its `preDispatchBlobs` (never `git checkout -- <paths>`), record `REGRESSED (scope violation)`, and re-apply that finding with the coordinator's own hand (§10.4 step 2's fallback — a scope offender never gets a second applier, in either cadence). Note it in the round note; a repeat offender in the same round sends the whole round serial.

**Step 4 — Test the union (fast path), fall back to serial for attribution.** Run the affected modules' tests once over all parallel-applied fixes.

- **Pass** → every fix is a commit candidate; continue to §10.4b unchanged.
- **Fail** → revert **all** parallel-applied paths, then re-apply the same findings **serially** per §10.4 steps 2–4 so the checkpoint attributes the regression to one finding. Record `serial-fallback r<N>` in the round note.

The fallback preserves §10.4's guarantee: a failing union test cannot say which fix broke it, and guessing would discard good fixes. Parallel application is therefore a **latency optimization only** — the same rule §10.4 step 5 states for batching — and never widens what gets reverted or weakens what gets attributed.

**§10.4b runs on every fix regardless of how it was applied.** An applier-applied fix — serial or parallel — gets exactly the same per-fix verification as a coordinator-applied one; that check is what makes the delegation acceptable, so it is never skipped for the fixes that most need it.

#### 10.4b Verify each fix against its finding

Runs after §10.4 and before §10.5, on every fix that survived its checkpoint. **This is the only in-round evidence that a fix addresses its finding rather than merely compiling and passing the tests that already existed.** Without it the loop's sole signal that a fix worked is the *next* round's reviewers failing to re-raise it — a full round of latency, on a check §10.3 step 2 admits cannot distinguish "the fix didn't land" from "the reviewer is mis-flagging."

One agent per surviving fix, all dispatched **in a single message with `run_in_background: false` on every call** (§6's parallelism rule applies here exactly as it does to reviewers — and note that §6 governs *batching only*; the blocking flag is SKILL.md Hard rule 1, and citing §6 alone has historically been read as covering both):

- `subagent_type` = `critical-thinking` unless the roster supplies a better skeptic.
- `description` = `"Verify fix: <severity> <file>:<line>"`.
- `prompt` = the expanded [fix-verification brief](agent-briefs.md#7d-fix-verification-brief-template) (§7d): the finding verbatim, that fix's diff, **constructed differentially** — diff the current tree against this fix's `preDispatchBlobs`, restricted to its differential path set (§10.4 step 3), never a bare `git diff -- <paths>`. On the serial cadence nothing is committed until §10.5, so a bare path-scoped diff of a shared file carries every earlier finding's hunks, and the verifier would rule on work the finding never claimed — `NOT_FIXED` for someone else's edit, or `FIXED` on the strength of it, and the step-1 test if one was written. It receives **neither the other fixes, nor the review report, nor the reviewer attribution** — same authority-signal reasoning as §5A.5a step 3.

**Coordinator pre-check, before any verifier is dispatched: did the fix touch the step-1 test?** Compare the step-1 test file and every fixture/helper it reads **byte-for-byte against `preDispatchTestBlobs`** (§10.4 step 3). Any difference — rule `NOT_FIXED` outright: do not dispatch a verifier, and do not rerun the test to see whether it passes. **This must not be a path comparison against the differential set**, which by construction can never contain the test: step 1 writes it before the snapshot, so an existing test file is subtracted out as part of `preDispatchPaths` and a new one is untracked and invisible to `git diff --name-only` on both sides. A path check here is dead code that reads as enforcement. **Restore the test and its fixtures from `preDispatchTestBlobs` before doing anything else**, so the tampering cannot become the next finding's baseline (§10.4 step 3's fourth assertion states the same rule at the earlier detection point; they are deliberately redundant because either may fire first, and both mandate restoration). The applier was handed a pass/fail criterion plus write access to the code under it; the cheapest path from "my edit doesn't pass" to `APPLIED: yes` is weakening the assertion, and step 4's checkpoint reruns *that same test*, so it inherits the tampering rather than catching it. A test the fix edited is not evidence about the fix. Record `FIX_FAILED (test modified)` and defer it to the final report with the offending paths; on a CRITICAL this fires §10.6's stop, which is the intended outcome. This is a check on the diff, not a question put to an agent — §7e's immutability rule states the prohibition, and this is what enforces it.

| Verdict | Coordinator action |
|---|---|
| `FIXED` | Commit it (§10.5). |
| `PARTIAL` — **HIGH/MEDIUM** | **One** retry: re-edit with the verifier's reasoning appended to the finding, re-run steps 2–4, re-verify once. A second `PARTIAL` is committed anyway **and** left out of `priorFindingsFingerprints`, so next round's reviewers get a fresh look at it rather than the loop calling it done. |
| `PARTIAL` — **CRITICAL** (decision #70 extends its inversion here) | Same one retry. A **second** `PARTIAL` does **not** commit — revert this finding's changes by restoring §10.4 step 3's `preDispatchBlobs` (never `git checkout -- <paths>`), record `FIX_FAILED (partial, unretried further)`, and defer to the final report. Two consecutive PARTIAL verdicts are not ambiguity (the verifier engaged both times and rendered a real judgment), but the underlying risk is the same one #71 exists for: an under-resolved CRITICAL committed on the theory that "next round will catch it" is exactly the failure mode delegation was supposed to avoid, not court twice. |
| `NOT_FIXED` | Revert this finding's changes by restoring §10.4 step 3's `preDispatchBlobs` (never `git checkout -- <paths>`), record `FIX_FAILED`, and defer it to the final report with the verifier's reasoning. **Do not retry** — the editor and the verifier now disagree about what the finding asks for, which is a specification problem an extra edit cannot settle. |
| agent failed / unparseable verdict — **HIGH/MEDIUM** | **Re-dispatch the verifier once**, exactly as for CRITICAL below — no verdict was rendered, so there is nothing to settle and the retry is free of `NOT_FIXED`'s objection. If the second attempt also fails: revert this finding's paths, record `FIX_FAILED (unverified)`, count it in `fixVerifyTotals.unverified`, note `fix-unverified r<N>`, and continue the round. **The fix does not commit.** |
| agent failed / unparseable verdict — **CRITICAL** (decision #70, bounded by #73) | **Re-dispatch the verifier once.** No verdict was rendered, so `NOT_FIXED`'s "an extra edit cannot settle a disagreement" objection does not apply — there is no disagreement, only a missing reading. If the second attempt also fails: revert this finding's paths, record `FIX_FAILED (unverified)`, defer to the final report, and **continue the round** — §10.6's carve-out makes this the one `FIX_FAILED` qualifier that is not round-fatal on a CRITICAL. The fix still does not commit (a flaky verifier gives no basis to guess the edit was right, and this is the class where a wrong guess ships), but a crashed agent is an infrastructure event, not a finding about the code, and must not kill every other fix in the round. |

**A `FIXED` verdict also enters `verifiedFixed`** as `{symbol, file, finding: <the round report's one-line description of this specific finding>, evidence: <the verifier's REASON>, round}`, where `symbol` is the finding's `enclosing_symbol` from §10.3 step 2. **Leave `settled_head` and `blob` unset — §10.5 step 7 stamps them.** They cannot be captured here: the fix is still uncommitted, so `HEAD` is the commit the round *started* from, and stamping it would mark the entry stale the moment the round's own fix commit lands. The same holds for a `refutedFindings` entry (§10.3 step 3): record it unstamped — and note that step 7 stamps it against the **round-start** commit, not the post-fix one, because the refuters read the round-start tree; a fix landed later in this same round therefore reopens the claim rather than shipping it as settled. The two bindings are what make the subtraction expire: once a later round edits that file, **or lands any commit at all**, the entry is rendered as re-verify, not as out of scope (§10.1). This is the only way a finding leaves later rounds' scope (§10.2 step 0) — **the exact finding, not its symbol**: a second, different defect sitting in the same function or class is unaffected and stays fully in scope, because §7d's verifier ruled on one claim, not on every invariant the symbol carries. `PARTIAL`, `NOT_FIXED`, and unverified fixes add nothing, so the next round reviews them again with no discount.

**A crashed verifier never commits, at any severity.** Both rows agree: **re-dispatch once, and if no verdict comes back, revert and record `FIX_FAILED (unverified)`.** Nothing is lost by declining to commit — the finding is recorded in `fixOutcomes` and rendered in §10.7 regardless. Committing instead would **push an edit no agent ever verified onto the PR's branch** and report it only in `fixVerifyTotals.unverified`, where a reader scanning a green round would not look — a silent failure of exactly the class this skill exists to catch. The stricter rule costs one extra round.

The contrast with §5A.5a's `UNCERTAIN`-upholds rule holds unchanged: there, ambiguity fails *toward keeping a finding*, because dropping a real CRITICAL is terminal and silent. Here it fails *toward not committing*. In both cases the tie-break runs away from the irreversible, unobservable outcome.

**The verifier never edits.** It reads the finding and the diff and rules. A verifier that patched the fix would be an unreviewed second author on the same change, and its next verdict would be on its own work.

### 10.5 Per-iteration: commit + push

**One commit per finding, not one per round.** A round-sized commit cannot be reverted per-finding once pushed — which is exactly what a human needs when round 2 dislikes one of round 1's five fixes. On a squash-merged PR the extra commits cost nothing; on a merge-committed one they *are* the review-iteration trail.

For each `FIXED` (or retried-`PARTIAL`) fix, in the order applied:

1. `git add` only that finding's paths plus its §10.4 step-1 test. Never `git add -A`.
2. `git commit -m "fix(<scope>): <finding one-line summary>"`. The body cites the finding as `<severity> <file>:<line>`, the round number, and the verifier's verdict.
3. **If the pre-commit hook fails, fix the cause — do not bypass it.** Reproduce with stderr non-TTY (`bash .githooks/pre-commit >/dev/null 2>&1; echo $?`), because a hook that passes at a terminal can still fail under the harness and the TTY is the discriminator. The usual causes are a stale generated file the hook re-staged (regenerate it and include it in the pathspec) or a real lint/test failure — which is the hook working. **`git -c core.hooksPath=/dev/null` is not an escape hatch and must not appear in a loop commit**; a hook exists to stop exactly the class of thing an automated fix round is most likely to get wrong.

Then, once for the round:

4. Regenerated docs (§10.4 step 7) go in their own commit: `chore(docs): regenerate <artifact> after round N`.
5. Push **once**, after all of the round's commits — one push per round, not one per finding — and push with a lease, never plain: `git push --force-with-lease=<branch>:<roundStartOid>`, where `<roundStartOid>` is the PR head this round started from (`gh pr view <ref> --json headRefOid --jq .headRefOid`, read at round start). The lease is the guard, not a preceding read: a plain `git push` after a `gh pr view` check leaves a check-to-push window another actor can move the branch in, while the lease is evaluated by the remote against the ref itself and refuses if it no longer points at `<roundStartOid>` — divergence, a rewind, and a deleted branch all fail the same way. Re-reading `headRefOid` immediately before the push is still worth its one API call as an early, readable diagnosis, but it decides nothing. **Any nonzero push exit → do not retry, do not reconcile:** stop the loop with `STOPPED_REMOTE_HEAD_MOVED` (§10.6) and write `stateFile` with `stop_reason: STOPPED_REMOTE_HEAD_MOVED` **before exiting** — step 7 has not run yet at this point, so without that write the round's commits sit locally with no checkpoint and the next invocation restarts as a fresh loop against a branch it has not read. Record both OIDs (round start, and what the PR head is now) plus the push's stderr in the reason, so the human can see what landed under the round. Do not fetch, rebase, merge, or re-push with `--force` to reconcile it — the loop reviewed code the branch no longer has.
6. Increment `iterationsCompleted`; update `findingsFixedThisRun`, `fixOutcomes`, and `fixVerifyTotals`.
7. **Write `stateFile`** (schema in `${CLAUDE_PLUGIN_ROOT}/skills/zord-multi-agent-review/scripts/loop_state.py`): `pr`, `branch`, `head` (= `git rev-parse HEAD` after the push), `max_iterations`, `iterations_completed`, `status` (`"in_progress"` here; §10.3 step 1 writes `"approved"` on the terminal APPROVE, which is what makes `check()` report `COMPLETE` instead of resuming the round that just approved), the forwarded flags, `rounds` (one entry per completed round: `round`, `verdict`, `roster`, `axes`, `files_read`, `fixes_landed`, `fixes_reverted`, `checkpoint: "round-<N>.json"`), `verified_fixed` and `refuted` (each entry carrying its `file`, recorded unstamped by §10.4b — the top-level `head` is this round's push and never substitutes for a per-entry one), `prior_findings_fingerprints`, `deferred`, `fix_outcomes`, and the two totals maps. Overwrite the whole file each round; it is derived from loop state, not appended to. Then, as the **last operation of the round**, run `python3 <plugin>/zord-multi-agent-review/scripts/loop_state.py stamp <stateFile> --round-start <roundStartOid>` — the same OID step 5 leased the push against. It binds each unstamped entry to the tree that entry was actually judged against: `verified_fixed` to the post-push `HEAD` (the verifier ran after the fix), `refuted` to `<roundStartOid>` (the refuters ran before it). Passing the round start is what stops a same-round fix from laundering a refutation into the next round's DO-NOT-RE-RAISE list — a fix can make a previously false claim true, so a round that committed anything reopens its own refutations as RE-EXAMINE, while a round that committed nothing (round start == `HEAD`) keeps them excluded. Each `blob` is recomputed against that same commit; a file absent there leaves `blob` null, so the entry re-verifies rather than silently excluding itself. The top-level `head` is rewritten to the post-push `HEAD`, and the file is replaced atomically (temp file, fsync, rename), so an interrupted stamp leaves the previous checkpoint intact rather than half a JSON document. The stamp must run after the commits, never before — doing it by hand at verification time expires every fix the round just landed. Write the file with the same discipline as the round checkpoints: never staged or committed, and a failed write is noted once and never stops the round — but say so, because the next round then carries nothing and a dead session cannot resume.

### 10.6 Loop control & safety stops

Continue the loop only if:

- VERDICT was NEEDS_CHANGES or BLOCK (not APPROVE). Exception: an APPROVE that fails the §10.3 coverage acceptance gate does not end the loop — it triggers the single sharpened re-dispatch (not counted as an iteration); a second empty-coverage APPROVE stops the loop.
- `iterationsCompleted < maxIterations`.
- No regression (§10.3 step 2).
- No **round-fatal** fix failure. A single fix that regresses or verifies `NOT_FIXED` no longer stops the loop — §10.4 reverts that fix alone and the round continues with the rest. Stop only when:
  - **every** fix attempted in the round ended `REGRESSED` or a **round-fatal** `FIX_FAILED` → `STOPPED_NO_FIX_LANDED`. Nothing is pushable and the next round would re-derive the same findings against the same code. **"Round-fatal" is load-bearing here, not decoration:** without it a round whose single finding is a CRITICAL ending `FIX_FAILED (unverified)` satisfies this bullet and stops anyway, silently defeating the carve-out below — and decision #69's own stated motivation is "the common small round (1–3 findings)," so the one-finding case is the normal case, not a corner. A round that lands nothing but whose only non-landing outcome is `(unverified)` continues, and the loop's next round re-reviews the reverted finding.
  - a **CRITICAL**'s fix ended `REGRESSED` or `FIX_FAILED` → `STOPPED_CRITICAL_UNFIXABLE`. A blocker the coordinator could not land is a human-judgment moment, and continuing would push lower-severity fixes on top of an unresolved CRITICAL.

    **Qualifier carve-out — `FIX_FAILED (unverified)` is NOT round-fatal.** Every other `FIX_FAILED` qualifier is a judgment about the code: `NOT_FIXED` means the verifier read the diff and ruled against it, a second `(partial, ...)` means it engaged twice and rendered a real verdict both times, `(test modified)` means the applier edited its own gate. `(unverified)` means the verifier *process* failed — a crashed agent or unparseable text — which carries **zero information about the fix**. Stopping the round on it lets an infrastructure event masquerade as "this CRITICAL is unfixable," reverting a tested, checkpoint-passing edit and killing every other finding's fix with it.
    Handling: **re-dispatch the verifier once** (this is the one retry `NOT_FIXED` is denied, and for the opposite reason — there is no disagreement to settle, only a missing verdict). If the second attempt also fails, revert this finding's paths, record `FIX_FAILED (unverified)`, let the round continue, and surface the CRITICAL as unresolved in §10.7 with the verifier's failure mode. The fix is still not committed — unverified is not "assume fixed" — but the round is not fatal.
    **The default is fatal; escaping requires an entry here.** A qualifier that is not named in this carve-out is round-fatal on a CRITICAL, so a future qualifier cannot slip past this gate by being unrecognised — it fails closed. Any new qualifier must state its §10.6 disposition when it is introduced.
- No repeated empty-coverage APPROVE, and no APPROVE whose engagement ratio is below `ceil(n/2)` (§10.3 step 1 → `STOPPED_NO_ENGAGEMENT`).
- **The round returned a usable report** — §10.3 step 0b(i) classified the return as the §10.2 schema. A `ROUND-FAILED:` sentinel, or any return that is not the schema, → `STOPPED_ROUND_UNUSABLE`. **Unconditional.** The coordinator cannot triage what it cannot parse, and the alternative — inferring a verdict from a malformed return — is fabrication on the path that commits and pushes. Carry the inner pass's `<reason>` into §10.7 verbatim so the human sees which hard-fail fired rather than only that the round died.
- **The round's fan-out actually happened** — §10.3's dispatch reconciliation gate found `returned == dispatched` and the `Reviewers:` line was present, and the round subagent did not return `DISPATCH-FAILED`. Otherwise → `STOPPED_DISPATCH_UNAVAILABLE`. **Unconditional, and it is not traded off against how many fixes landed**, for the same reason as the two applier stops above: the coordinator cannot know what a lost lane would have found, so it cannot weigh its absence. This stop replaces the withdrawn inline fallback (§10.2 step 3) — the loop now refuses a round it cannot prove was reviewed in parallel, rather than accepting one agent's word for four lanes and then committing against it.
- **No applier escaped its owned set into a commit** — §10.4 step 3's HEAD assertion found `git diff --name-only preDispatchSha <moved-HEAD>` exceeding the owned set → `STOPPED_APPLIER_ESCAPED_SCOPE`. Unconditional, like the push stop below and for the same reason: the coordinator has no snapshot for paths it never granted, so it cannot prove what was changed or restore it.
- **The PR head is still where the round started** — §10.5 step 5's `git push --force-with-lease=<branch>:<roundStartOid>` succeeded; the lease, not the advisory `gh pr view` re-read, is what decides this. Any nonzero push exit (lease refused, branch rewound, branch deleted, or any other failure) → `STOPPED_REMOTE_HEAD_MOVED`, with `stateFile` written carrying that `stop_reason` before exiting. Unconditional: this round's findings were derived from a tree the branch no longer has, so pushing fixes over it would commit a review of code nobody is merging. Distinct from `STOPPED_APPLIER_PUSHED`, which is this loop's own applier exceeding its brief; here the mover is outside the loop entirely and nothing the coordinator did is wrong — only the branch moved.
- **No applier reached the remote** — §10.4 step 3's upstream assertion (serial) or §10.4a step 3's batch-level one fired → `STOPPED_APPLIER_PUSHED`. A dispatched applier pushed to the live branch, which the coordinator cannot undo and which invalidates every guarantee §10.4 makes about what is on the remote. This is the one stop condition caused by an agent exceeding its brief rather than by the code, and it is unconditional: it is never traded off against how many fixes landed. Note §10.4 step 3 evaluates its assertions **unconditionally and combines verdicts, fatal winning** — precisely so this condition is not permanently shadowed by the HEAD-moved check, since an applier cannot push without first committing.

If any stop condition fires, write `stateFile` first (§10.5 step 7, with the stop token in a `stop_reason` field so a resume knows the loop was stopped rather than cut off), then emit the final report (§10.7) explaining which condition stopped the loop. **Never silently continue past a stop condition** — surface it.

**Adding a stop condition is a three-section edit, by policy.** The token must be named here, produced at its detection site (§10.4 / §10.4a / §10.3), and given a row in §11 — and the name must be the same string in all three, never a gloss like "the sibling case of X". Every stop condition this spec has lost track of was lost by being defined at one of those three sites and not the other two; this list is exhaustive by construction, so a condition absent from it means the loop **continues** past it. Same discipline §10.1 states for `FIX_FAILED` qualifiers, and for the same reason.
