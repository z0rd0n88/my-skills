# multi-agent-review — Anti-patterns

> Reference file for [`../SKILL.md`](../SKILL.md) (multi-agent-review): the behaviors this skill must never do, with the rule/decision each one guards.

## 12. Anti-patterns

- **Don't delegate *triage* to another subagent.** Deciding which MEDIUM applies to this PR, which the author would push back on, and what the fix should be requires project context a sub-fixer lacks. Mechanically applying an already-specified fix is a different job — §10.4 step 2 licenses it serially for every HIGH/MEDIUM, §10.4a gates only running appliers *concurrently*, and both only because §10.4b verifies the result. Delegating the judgment remains wrong.
- **Don't let two appliers own the same file.** One working tree, two concurrent editors, and the second write silently eats the first. Ownership sets are computed pairwise-disjoint by the coordinator before dispatch and verified against the actual diff afterward — an overlap is a bug in the assignment, never something to reconcile after the fact.
- **Don't let an applier run git — ever. Don't let it run a test unless it was handed one.** These are two rules, not one.
  - **git is unconditional.** No add, commit, stash, checkout, or diff-and-revert, in either cadence. Every git operation mutates state the coordinator owns, and a `checkout` from an applier reverts work it does not own.
  - **Tests are gated on cadence, via block presence** (§7e, decision #75). In a **parallel batch** the applier gets no `{{FAILING_TEST}}` block and runs nothing: the tree holds every other applier's in-flight edits, so a test there can pass on broken code or fail on correct code — the result is not merely redundant, it is *misinformation*. In a **serial dispatch** the applier gets exactly one licensed test and running it is REQUIRED.
  - **Which argument is operative:** "the coordinator reruns it moments later, so it buys nothing" is **correct for the parallel batch and wrong for the serial path**. Serially it buys something real but non-load-bearing — the applier catches its own miss before the checkpoint does, turning a revert-and-fall-back-to-coordinator cycle into a corrected edit. Correctness still rests entirely on §10.4 step 4's checkpoint, which is why the licensed test is never a substitute for it.
- **Don't batch a CRITICAL's fix into the parallel path.** §10.4a's no-CRITICAL precondition stands (decision #71): the batch's safety case rests on a union test that cannot attribute a failure to one finding, and CRITICAL is exactly where that ambiguity is least tolerable. CRITICAL is always applied via §10.4 step 2's serial dispatch — one applier, one immediate checkpoint — which delegates it like any other severity but never lets it share a test run with another fix.
- **Don't let a serially-dispatched applier return without running the test it was handed.** When §7e's `{{FAILING_TEST}}` block is present, running it is required — it exists so the applier catches its own miss before the coordinator's checkpoint does. **Condition on the block, never on the severity label**: a batched HIGH has no block and must run nothing, so "CRITICAL/HIGH always runs its test" is false. It is not a replacement for §10.4 step 4 — the coordinator reruns the full affected-module suite regardless.
- **Don't let an applier edit the test it is being judged by.** §7e hands CRITICAL/HIGH appliers the step-1 test so they can confirm their own edit — which also hands them the gate. Weakening the assertion is the cheapest way to a passing test, and step 4's checkpoint reruns that same test, so it inherits the tampering instead of catching it. The prohibition in §7e's RULES is not the control; §10.4b's diff pre-check is (decision #73). Never satisfy yourself that a modified test passing means the fix landed — rule `NOT_FIXED` and don't rerun it.
- **Don't let a verifier ambiguity commit, at any severity.** Decision #58's "unparseable verdict counts as FIXED" was inverted for CRITICAL by #71 and is now withdrawn for HIGH/MEDIUM too (§10.4b): **re-dispatch the verifier once, and if it fails again revert this finding's paths, record `FIX_FAILED (unverified)`, and defer to the final report — do not fall back to a coordinator hand-edit.** (The one retry is #74; it is not the retry `NOT_FIXED` is denied, because a crashed agent left no verdict to disagree with. #74 also keeps this outcome from stopping the round — reverting the fix is right, killing every other finding's fix over an agent crash is not.) The asymmetry that makes #58 correct for HIGH/MEDIUM (an extra round costs little) is precisely what doesn't hold at CRITICAL, where a half-fixed vulnerability committed on a flaky verifier is the failure mode delegation was supposed to avoid, not court. A hand re-apply would be worse than the commit it replaces: it skips re-verification entirely, so the round would ship an *unverified* CRITICAL edit while reporting the verification stage as having run — and because `FIX_FAILED` on a CRITICAL fires a §10.6 stop, routing around it also silently converts a loop-halting condition into a continuing round. "The coordinator's own hand" is the fallback for an applier **refusal** or a **scope violation** at apply time (§10.4 step 2, §10.4a step 3) — never for a verification outcome.
- **Don't skip §10.4b for a parallel-applied fix.** Per-fix verification is the check that makes delegation acceptable; skipping it on delegated fixes inverts the safety argument.
- **Don't loop on LOW findings.** A LOW today is a LOW tomorrow; iterating on style nits is the treadmill failure mode.
- **Don't auto-merge after APPROVE.** The human owns merge approval. The loop ends at "ready for human review," not "merged."
- **Don't call a PR merge-ready with PENDING open questions.** APPROVE answers "is the code right"; an open question asks "is this the right code". The author dispositions each one (ANSWERED / FILED / DECLINED) before merge, and the final report lists what is still pending instead of hiding it under the verdict (§10.7).
- **Don't run the smoke test on every round.** Smoke is expensive (port binding, DB, full app boot). Run only when the fix actually touched code the smoke exercises.
- **Don't suppress reviewer disagreements.** When two lanes contradict, the coordinator picks the safer side and **says so** in the round's commit message and the final report.
- **Don't accept a "no disagreement" claim from a round you cannot prove ran in parallel.** One author cannot genuinely disagree with itself, so an empty `## Reviewer Disagreements` alongside a fully-engaged roster is a tell that the fan-out collapsed, not evidence the lanes agreed. **It is a tell, not a gate** — no stop condition in §10.6 fires on it. What loop mode does hard-stop on is narrower and structural: a `DISPATCH-FAILED` return, a `Reviewers:` count mismatch, or a missing `Reviewers:` line (§10.3 step 0b). A round that reports `6/6 returned` with an empty disagreements block passes every gate, so this remains something a human weighs in both modes.
- **Don't summarize the orchestrator's return.** The subagent exists to keep worker transcripts out of the caller's context, not to shrink the deliverable. A caller that condenses the report before printing has spent the agents and thrown away what they produced.
- **Don't let a subagent that can't spawn workers run the review anyway.** One agent playing five lenses returns something shaped like a multi-perspective review with none of the independence — and its refuters share an author with its findings. `DISPATCH-FAILED` then an inline re-run is the correct outcome; a plausible-looking report is the dangerous one.
- **Don't add a third dispatch layer.** Two is the contract (§5A.0). A loop round is already layer 1; the harness does not guarantee a subagent can spawn subagents, so every added layer is another way for the fan-out to collapse into a single agent without saying so.
- **Don't let refuters see who filed the claim, or how many reviewers filed it.** Both are authority signals, not evidence, and a skeptic told "three reviewers found this" will uphold it. The stage buys independent samples; attribution spends them.
- **Don't give every refuter the same lens.** Three copies of "is this real?" is one opinion sampled three times — they fail together on whatever the shared framing misses. Different lenses is the entire reason the majority vote means anything.
- **Don't fix a DROPPED finding "just to be safe."** It lost an evidence contest; editing the PR anyway makes the stage a decoration and reintroduces exactly the false-positive edits it exists to prevent. If you disbelieve a refutation, overrule it explicitly in the report and say why — don't route around it silently.
- **Don't let UNVERIFIED read as clean.** A finding the budget skipped was never challenged. Tag it, render it in its own subsection, and treat it at full severity in triage.
- **Don't refute the `critical-thinking` output.** Questions have no truth value to attack; you get noise and lose the one lens that isn't playing the severity game (§9).
- **Don't run refutation after the severity budget.** Capping HIGHs first spends the budget ranking findings that are about to be dropped, and can demote a true HIGH to make room for one that refutation would have removed.
- **Don't accept an APPROVE with an empty Confirmed-coverage list.** An APPROVE that validated nothing is an opinion, not a coverage report. Re-dispatch once with the unexamined paths named; stop for a human if it repeats (§10.3 step 1).
- **Don't revert a whole round because one fix regressed.** Five good fixes discarded to punish one bad one, and the attribution of *which* fix broke it thrown away with them. Checkpoint per finding and revert per finding (§10.4 step 4).
- **Don't bundle a round into one commit.** Once pushed, a round-sized commit cannot be backed out per finding — which is precisely what a human wants when the next round dislikes one of the last round's fixes.
- **Don't bypass the pre-commit hook to land a fix round.** `git -c core.hooksPath=/dev/null` in an automated loop disables the check most likely to catch what the loop just got wrong. A failing hook is a cause to find, not a flag to add.
- **Don't put line numbers in the regression fingerprint.** Every fix shifts the lines below it, so a line-bearing hash stops matching exactly when the round did the most editing — the check silently fails at its most important moment (§10.3 step 2).
- **Don't treat a reverted fix's re-raise as a regression.** `REGRESSED` and `FIX_FAILED` findings were never claimed fixed; seeing them again next round is the system working, and stopping the loop over it burns a round for nothing.
- **Don't let the fix verifier edit, or see the other fixes.** An editing verifier is an unreviewed second author whose next verdict is on its own work; a verifier shown the whole round grades the round's momentum instead of one diff against one finding.
- **Don't ship a fix for a CRITICAL without a test that failed before it.** The test is the only artifact that still proves the fix was necessary three refactors from now, and it is the one regression anchor immune to line drift and reviewer rewording (§10.4 step 1).
- **Don't close a finding on forked prose by fixing only the fork.** When the flagged sentence was copied from an ancestor skill, grep the ancestor for it and record the verdict there — fixed, or why it does not apply — before closing the finding. The ancestor still carrying the sentence means the next fork inherits the defect, so fixing only the copy is not a fix.
